**How to read it:**

- **Glossary.** Every domain term is defined once in §3 and used verbatim everywhere else.
- **Requirement IDs.** Features (§4) carry globally numbered requirements, FR-1 … FR-31. IDs are stable and never renumbered. FRs are grouped by feature, so numbers are not always in order: FR-28, FR-29 and FR-31 sit in §4.1, and FR-30 in §4.3. A range such as "FR-11 … FR-16" means those numbers only. FR-14, FR-15 and FR-29 are each split into an **a** part (Core) and a **b** part (Extension), so that no requirement has two priorities. The letter keeps the number stable.
- **Traceability.** The "Realized by" line of each user journey maps the journey to its FRs. FR-2, FR-4, FR-17, FR-26, FR-27 and FR-30 are support requirements, listed under "Support requirements" at the end of §2.4. "Realizes UJ-N" notes on FRs are shortcuts for the main journeys.
- **Rule IDs.** Validation rules keep the IDs from the brief: F1–F4, R1–R7 and W8–W15, plus F5 added by this PRD. The same rule has the same ID in the brief, this PRD, the stories and the tests. R3 and R4 are retired and their IDs are not reused.
- **Priority.** Every FR has a priority, **Core** or **Extension** (§7.1). Core is the flow that must be finished and stable first: *create job → generate supplier file → import → change view → approve → dashboard*. The **Core minimum** (§7.1) is the smallest part of Core that works end to end, and is built first.
- **Success metrics.** SM-1 … SM-12 correspond to success criteria 1–12 in the brief. SM-13 … SM-16 and the counter-metrics SM-C1 and SM-C2 are added by this PRD.
- **Assumptions.** Inferences not yet confirmed are tagged `[ASSUMPTION]` inline and listed in §11. All assumptions of PRD v1 and v2 were confirmed by the project owner on 2026-11-25, and none are open.
- **Addendum.** Technical hints, template build details and screen sketches live in `addendum.md`.

**All data in PTS, this PRD and the repository is fictional.** No real company, project or supplier names are used anywhere in the repository (NFR-8).

## 1. Vision

PTS is an internal web application that gives a production planner one reliable overview of production jobs placed with external suppliers. It answers one question quickly: *"Where is this job, and is there anything we need to act on?"*

Suppliers never get access to the company's systems. Instead, PTS generates a controlled Excel file per supplier with the same fields the planner sees in the app. The supplier fills in the date each stage was completed, whether a job is stopped and why, an expected delivery date and any issues, and returns the file. PTS checks every row, shows exactly what would change, and updates the job data only when the planner approves.

The value is trust in the data. Today, status lives in scattered Excel files and emails, and it is hard to know which version is current. PTS does three things:

- it makes the database the single current picture
- it makes every change traceable to an approved import or a recorded manual update
- it makes problems visible early: stopped jobs, jobs waiting for inspection, delays, and suppliers working from an outdated drawing revision

### 1.1 Long-Term Direction

v1 covers the supplier part of a longer flow. The long-term direction is a tracking system that follows a job from start to finish:

**Engineering → Supplier Production → Inspection → Delivery → Internal Assembly → Final Approval**

The capabilities deferred from v1 are listed in §7.2. A further later step is measuring business effects once baseline numbers are available, such as less time spent on manual follow-up and fewer errors from outdated revisions.

PTS should stay simple and focused, and should not duplicate ERP, PDM or quality systems.

## 2. Target User

### 2.1 Jobs To Be Done

- **Functional:** know the current stage of every job at every supplier without phoning or emailing around.
- **Functional:** send a supplier a clear, up-to-date list of their jobs, grouped by room, and get structured updates back.
- **Functional:** record what a supplier says on the phone, and be warned when a later file disagrees.
- **Functional:** catch problems early: a stopped job, a job waiting for inspection, a delay, or a supplier still working from an old drawing revision.
- **Contextual:** work within a controlled IT environment where suppliers cannot access internal systems, and file transfer happens by email or a shared folder.
- **Emotional:** be confident that nothing in the job data changed without the planner seeing it.

### 2.2 Users in v1

- **Production planner** — the one internal role in v1. Creates jobs, imports job packages, generates supplier files, imports returned files, approves or rejects imports, records manual updates, registers new drawing revisions and deliveries, and follows up from the dashboard.
- **Supplier** — an indirect user. Never uses PTS. Only receives and returns the supplier file.

### 2.3 Non-Users (v1)

- Project, engineering, quality and inspection personnel as separate roles (later versions).
- Suppliers as direct users of PTS.

### 2.4 Key User Journeys

The persona is fictional: **Ingrid, production planner** at a marine engineering company, responsible for about 150 open jobs across five suppliers of welding and surface treatment. Screen labels are shown in English with the Norwegian label in italics where it helps. Terms such as *pending import*, *change view*, *supplier-changed cell* and *conflict field* are defined in §3, and rule IDs (W8, W15 …) in §4.3.

**UJ-1. Ingrid registers new jobs and sends Leverandør Alfa their file.**
- **Entry state:** PTS is open in the browser on her desktop. There is no login in v1.
- **Path:**
  1. She opens **Import job package** (*Importer jobbpakke*), selects Leverandør Alfa and uploads an Excel file that lists the drawings to be produced, with room, drawing number, revision and due date.
  2. PTS shows a preview: the jobs it will create, and the rows it skips and why. She confirms, and PTS creates the jobs with generated Job IDs. For a single extra job she can use **New job** (FR-1).
  3. She opens Leverandør Alfa and clicks **Generate supplier file** (*Lag leverandørfil*).
  4. PTS downloads an `.xlsx` file. It holds all of Leverandør Alfa's open jobs sorted by room, a unique Export ID and the current values pre-filled.
  5. She attaches the file to an email to the supplier, outside PTS.
- **Climax:** the file opens in Excel with locked grey columns, yellow editable columns and dropdown lists in Norwegian. She knows the supplier can only enter dates in the stage columns.
- **Resolution:** the export is recorded, and the dashboard shows the date each job was last sent. Jobs with a new-revision mark lose the mark, because the supplier now has the updated file.
- Realized by FR-1, FR-6 … FR-10, FR-31.

**UJ-2. Ingrid imports Leverandør Alfa's returned file and approves it.**
- **Entry state:** Leverandør Alfa has emailed the file back. Ingrid saves it locally.
- **Path:**
  1. She opens **Import supplier file** (*Importer leverandørfil*) and uploads the file.
  2. PTS checks the file as a whole, then every row, and creates a pending import.
  3. The change view shows, per job, the cells the supplier changed (value in PTS → value in file), which rows are rejected and why, and which rows carry warnings.
  4. She sees that PTS-0003 is now stopped with the reason *Mangler materiale*, that PTS-0001 has a new *Sveiset* date, and that PTS-0002 reports revision B while the current revision is C.
  5. She clicks **Approve import** (*Godkjenn import*).
- **Climax:** the dashboard immediately shows PTS-0003 as stopped, PTS-0001 at a new active stage, and PTS-0002 with a revision mismatch flag. She knows exactly what changed, because she saw every change on one screen before approving.
- **Resolution:** the import is in the import log with date, file name, user and result. She phones the supplier about the outdated drawing.
- **Edge cases:**
  - The file is not a PTS supplier file (wrong columns, no Export ID). PTS rejects the whole file with a clear message, and no pending import is created.
  - A row has *Stoppet* = *Ja* without a reason. That row is rejected and shown with rule R2, and the other rows can still be approved.
  - A row has *Sandblåst* filled in but no *Kontrollert* date. The row is accepted, and once W12 is built (Extension) it is shown with that warning.
- Realized by FR-11 … FR-18, FR-21, FR-22, FR-24.

**UJ-3. Ingrid registers a new drawing revision.**
- **Entry state:** engineering has approved revision C of drawing DRW-10002. Ingrid has placed the drawing in the shared folder and emailed the project manager and job owner, as today.
- **Path:**
  1. She opens job PTS-0002 and changes the current revision from B to C.
  2. The job gets the flag *New revision — send updated file to supplier* on the dashboard. The stage dates stay as they are.
  3. Next time she generates Leverandør Alfa's file, the Revision cell of PTS-0002 is highlighted and the Revision note says `NY REVISJON`.
- **Climax:** the supplier cannot miss that the drawing has changed, and Ingrid cannot forget to tell them.
- **Resolution:** the flag disappears once the new file has been generated. If a file from an older export still reports revision B and is approved, the job gets the revision mismatch flag.
- Realized by FR-3, FR-10, FR-14a (W8), FR-24.

**UJ-4. Ingrid follows up in the morning, records a phone call and registers a delivery.**
- **Entry state:** start of the working day.
- **Path:**
  1. She opens the dashboard.
  2. She filters on *Stopped*, then *Ready for inspection*, then *Delayed*, then *New revision or revision mismatch*. She can also filter on a room.
  3. The supplier phones: the missing material for PTS-0003 has arrived. Ingrid opens PTS-0003 and records a manual update: *Material* gets today's date, and *Stoppet* is set to *Nei*.
  4. A delivery arrives for PTS-0001. She registers it as delivered with today's date, and the job closes.
- **Climax:** she has a short list of jobs to act on without opening any Excel file, and the phone call is recorded with her name in the job history.
- **Resolution:** she books an inspection for PTS-0004 and follows up the delayed jobs.
- Realized by FR-5, FR-23 … FR-25 and FR-29a. Step 3 (the manual update) is realized by FR-28 and is Extension.

**UJ-5. A returned file disagrees with the phone call (Extension).**
- **Entry state:** after the call in UJ-4, Leverandør Alfa returns the file Ingrid sent last week. In that file, *Material* for PTS-0003 is still empty, because the supplier forgot to update that row. For PTS-0005, Ingrid had recorded *Sveiset* = 20.11.2026 by hand after the export, and the supplier has now entered 21.11.2026.
- **Path:**
  1. Ingrid uploads the file.
  2. The change view shows a notice at the top: *1 konflikt må vurderes*.
  3. PTS-0003: the supplier did not change *Material*, but PTS has a newer value. PTS keeps it, and the row shows **W15 Conflict with manual update** as information. No choice is needed.
  4. PTS-0005: the supplier changed *Sveiset*, and so did Ingrid. The field is a conflict field with W15. It shows both values and who set the PTS value and when. Ingrid phones the supplier and chooses **Use file value** for the field.
  5. **Approve import** is disabled until every conflict field has a choice, and shows how many remain. She approves.
- **Climax:** the conflict was impossible to miss, nothing was decided for her, and approving the file did not undo the phone call.
- **Edge case:** if Ingrid is unsure, she rejects the import and asks for a new file.
- Realized by FR-8, FR-14b (W15), FR-15a, FR-15b, FR-18, FR-28.

**UJ-6. Two returned files from the same supplier wait at the same time (Extension).**
- **Entry state:** Leverandør Alfa returned a file on Monday, from export 1, and that import is still pending. On Tuesday they return a file from a newer export 2.
- **Path:**
  1. Ingrid uploads Tuesday's file. PTS accepts it as a second pending import. Monday's import now carries W9 *Outdated file*.
  2. She approves Tuesday's import first.
  3. Monday's import is recalculated against the updated job data. A field that Tuesday's import has since changed, and that Monday's file sets to another value, is now a conflict field with **W14 Job changed by another import**.
  4. She chooses **Keep PTS value** for each of those fields, because Tuesday's values are newer, and approves Monday's import for the remaining changes.
- **Climax:** she sees which of Monday's values would overwrite Tuesday's newer ones, and keeps control over each.
- **Resolution:** both decisions, and the choices made, are in the import log.
- Realized by FR-14b (W9, W14), FR-15b, FR-18, FR-19, FR-20, FR-21.

**Support requirements.** These requirements are not part of one journey but make the journeys work: FR-2 (edit a job), FR-4 (manage suppliers), FR-17 (no change before approval), FR-26 (seed data), FR-27 (example files) and FR-30 (the stop reason follows *Stoppet*).

## 3. Glossary

**Jobs and revisions**

- **Job** — one drawing to be produced by one supplier. Has a Job ID, room, drawing number, current revision, supplier, due date, an optional area, stage dates, a stopped flag and other supplier-reported fields. Belongs to exactly one supplier.
- **Job ID** — unique identifier of a job, generated by PTS, for example `PTS-0001`.
- **Supplier** — an external workshop that produces jobs. Has a unique name and zero or more jobs.
- **Room** — the room a job belongs to. Suppliers produce one room at a time, so rooms group jobs in the supplier file and on the dashboard.
- **Area** — an internal grouping of rooms, for example a deck. Used for filtering by the planner. It is not included in the supplier file.
- **Drawing number** — identifier of the engineering drawing the job is produced from. Not unique: the same drawing can be produced more than once, for example two copies of every drawing in a package, or for another customer. Jobs are told apart by Job ID. The drawing itself lives outside PTS.
- **Current revision** — the drawing revision the job must be produced to, as registered in PTS. PTS stores only the current revision, not a history. Stage dates are kept when the revision changes.
- **New-revision mark** — a flag on a job. It is set when the production planner changes the job's current revision, and cleared when a supplier file containing the job is generated.
- **Open job** — a job that is not closed. Only open jobs are included in supplier files.
- **Closed job** — a job that has been closed, either automatically when it is delivered or by hand. FR-29a specifies delivery, and FR-29b closing and reopening by hand.

**Stages and status**

- **Stage** — one of six production steps, in this order: **Material** (the material is in place), **Welded**, **Inspected**, **Blasted**, **Painted**, **Final inspection**. Blasted and Painted together are the surface treatment.
- **Stage date** — the date a stage was completed. Empty means not completed. Filled in by the supplier, or by the planner as a manual update.
- **Active stage** — calculated: the first stage without a stage date. When all six stages have a date, the active stage is *Preparation and shipping* (*Klargjøring og forsendelse*) until the job is delivered. It is never typed in.
- **Delivered** — the date the production planner signed that the job was received. Not a supplier field and not in the supplier file. A delivered job is closed.
- **Stopped** — a flag, *Ja* or *Nei*, that a job cannot continue. It is independent of the stage. Requires a stop reason.
- **Stop reason** — one of `Drawing issue`, `Missing material`, `Check requested`, `Other`. Required when the job is stopped. `Other` also requires a comment.
- **Expected delivery date** — the date the supplier expects to deliver the job. May be empty.
- **Due date** — the date the job must be delivered, set by the planner per job.
- **Supplier-reported fields** — the six stage dates, stopped, stop reason, expected delivery date and comment. The only fields an import or a manual update may change.

**Supplier file and export**

- **Supplier file** — the `.xlsx` file PTS generates for one supplier, following the fixed template, with locked columns and editable columns.
- **Job package** — an `.xlsx` file the planner prepares that lists drawings to be created as jobs for one supplier. FR-31 specifies the import.
- **Export** — the stored record that a supplier file was generated: Export ID, export date, supplier, and every job and value the file contained.
- **Export ID** — unique identifier of one export, printed in every row of the supplier file.
- **Exported value (E)** — the value a cell had in the supplier file when it was generated, as stored in the export.
- **Current value (D)** — the value the job has in PTS now.
- **File value (F)** — the value in the returned file.
- **Supplier-changed cell** — an editable cell whose file value differs from its exported value (F ≠ E).
- **Conflict field** — a supplier-reported field that changed in PTS after the export (D ≠ E) and where the supplier-changed file value differs from the current value (F ≠ E, F ≠ D). The planner chooses between the two values. FR-15a defines all cases.

**Import and validation**

- **Import** — one uploaded supplier file, together with its validation result and change view. Has a state: `Pending`, `Approved` or `Rejected`.
- **Pending import** — an import waiting for the production planner to approve or reject it. In Core a supplier has at most one pending import (FR-11). Once FR-19 is built, several can exist at once, even for the same supplier.
- **File check** — a check on the uploaded file as a whole (rules F1–F5). A failed file check is a **file rejection**, and no import is created.
- **Rejected row** — a row in an import that broke a rejection rule (R1–R7). Never applied.
- **Rejected import** — an import the planner has rejected. Nothing is applied.
- **Warning** — a flag on a row or an import that does not stop approval (W8–W15). Shown to the production planner before approval.
- **Change view** — the screen showing, for one import, which supplier-changed cells would be applied (value in PTS → value in file), plus conflict fields, rejected rows and warnings.
- **Approve / Reject** — the production planner's decision on a whole import.

**Records**

- **Import log** — the permanent record of every approved or rejected import, including the choice made for each conflict field.
- **Manual update** — a change the production planner makes by hand to a job's supplier-reported fields, for example after a phone call with the supplier.
- **Job history** — the permanent record, per job, of every change to its supplier-reported fields and every delivery, close or reopen. Each entry is linked to an import log entry or to a planner action: a manual update, a delivery, a close or a reopen.

**Screens and flags**

- **Job register** — the screens where the production planner creates and edits jobs and sees a single job in detail, including its flags and job history. The dashboard is the overview across jobs.
- **Dashboard** — the main overview of jobs, with flags and filters.
- **Delayed** — a job whose expected delivery date is later than its due date.
- **Ready for inspection** — a job whose active stage is Inspected or Final inspection.
- **Revision mismatch (warning W8)** — a returned supplier file reports a revision other than the job's current revision. Calculated against current data whenever the import is shown (principle in §4).
- **Revision mismatch flag** — a flag on a job, set when an approved import reported a revision other than the job's current revision at approval. FR-24 defines when the flag is set and cleared. It is a different thing from the warning, which is recalculated each time the import is shown.

## 4. Features

**Principle for all of §4:** validation results and the change view of every pending import are always computed against the current job data. Any change to a job, whether from an approved import, a manual update or an edit in the job register, therefore shows up in every pending import that contains the job.

### 4.1 Job Register

**Description:** The production planner creates, views and edits jobs, creates jobs in bulk from a job package, records manual updates, registers deliveries, closes and reopens jobs, and manages suppliers. The job fields in the app are the same as the columns in the supplier file, so what the planner sees and what the supplier sees match. UX decides whether the register is a spreadsheet-like table or a table with a separate form (§10). Supplier-reported fields change through an approved import or a manual update, and both are recorded in the job history. Realizes UJ-1, UJ-3, UJ-4.

**Functional Requirements:**

#### FR-1: Create a job

**Priority: Core.** The production planner can create a job with room, drawing number, revision, supplier and due date, and optionally an area. Realizes UJ-1.

**Consequences (testable):**
- The five fields other than area are required. Saving without one shows which field is missing.
- Due date must be a valid date.
- The same drawing number can be used on several jobs. Each job has its own Job ID.
- PTS assigns a unique Job ID.
- A new job is an open job with no stage dates and *Stoppet* = *Nei*, and it appears on the dashboard immediately with the active stage *Material*.

#### FR-2: Edit a job

**Priority: Core.** The production planner can edit room, area, drawing number, supplier and due date of a job.

**Consequences (testable):**
- Supplier-reported fields are changed through FR-28, not through this form.
- Changing the supplier of a job that is in a pending import makes its rows in that import fail R6.
- Edits through FR-2 are not recorded in the job history (§7.2).

#### FR-3: Register a new revision

**Priority: Core.** The production planner can change the current revision of a job. Realizes UJ-3.

**Consequences (testable):**
- After saving a different revision, the job has a new-revision mark.
- Saving the same revision again does not set a new-revision mark.
- The stage dates are not changed by a new revision.
- A pending import that contains the job is recalculated against the new revision: a row reporting another revision gets W8.
- The previous revision is not stored on the job. Earlier imports in the import log keep the revision they reported (FR-16).

#### FR-4: Manage suppliers

**Priority: Extension.** The production planner can create a supplier with a name, rename it, and see the list of suppliers.

**Consequences (testable):**
- Supplier names are unique.
- Suppliers cannot be deleted in v1.

**Notes:** Core relies on the suppliers in the seed data (FR-26).

#### FR-5: Job detail

**Priority: Core.** The production planner can open a job and see all its fields, its stage dates and active stage, its flags (FR-24), its last export date and its job history. Realizes UJ-4.

**Consequences (testable):**
- The job detail shows every field listed in FR-23.
- The job history lists changes in time order, newest first, each with date and time, user name, source (import, manual update, delivery, close or reopen), field, old value and new value.

#### FR-28: Manual update of supplier-reported fields

**Priority: Extension.** The production planner can change a job's supplier-reported fields by hand, as a manual update. Realizes UJ-4, UJ-5.

**Consequences (testable):**
- The same rules as for imported rows apply (R1, R2, R5). A manual update that breaks a rule cannot be saved, and the rule ID and message are shown.
- A manual update that leaves a stage out of order (W12) can be saved, and shows the warning.
- Every manual update is recorded in the job history with date and time, user name (FR-22), field, old value and new value.
- A pending import whose export was generated before the manual update shows W15 for the affected fields (FR-14b, FR-15a, FR-15b).

**Notes:** What happens when a returned file disagrees with a manual update is decided by the planner per field in the change view (FR-15b). Rejecting the whole import remains possible.

#### FR-29a: Register delivery

**Priority: Core.** The production planner registers that a job has been delivered. Realizes UJ-4.

**Consequences (testable):**
- The planner enters a delivery date. It is suggested as today's date and cannot be in the future.
- The job is then a closed job, and the job history records who registered the delivery and when (FR-22).
- A delivery can be registered even when some stages have no date. The confirmation names the missing stages.
- A closed job is not included in the next supplier file (FR-6), is not shown on the dashboard by default (FR-25), and does not trigger W13.
- A row for a closed job in a returned supplier file is still validated and shown in the change view.

**Notes:** Until FR-29b is built, a wrongly created or cancelled job stays open.

#### FR-29b: Close and reopen a job by hand

**Priority: Extension.** The production planner can close an open job without a delivery, and reopen a closed job.

**Consequences (testable):**
- **Manual close:** the planner can close an open job without a delivery, for example a cancelled job. The job history records who closed it and when.
- **Reopen:** the planner can reopen a closed job. It becomes an open job again and keeps its stage dates. A delivery date is cleared.
- Closed jobs behave as in FR-29a.

#### FR-31: Import a job package

**Priority: Extension.** The production planner can create many jobs at once from a job package file. Realizes UJ-1.

**Consequences (testable):**
- The planner selects the supplier and uploads an `.xlsx` file with the columns *Rom*, *Område*, *Tegningsnummer*, *Revisjon* and *Frist*. A template is provided (`addendum.md`).
- PTS shows a preview before anything is created: the jobs it will create, and the rows it skips with the reason.
- A row is skipped when the room, drawing number or revision is missing, or the due date is not a valid date.
- A drawing number that already exists in PTS or earlier in the file is not skipped. It is shown with a warning in the preview, because the same drawing can be produced more than once, and the planner decides whether to confirm.
- Nothing is created until the planner confirms. Confirming creates all non-skipped rows as jobs in one all-or-nothing operation, each with a generated Job ID.
- Afterwards PTS shows how many jobs were created and skipped. Job packages are not stored in a log (§7.2).
- The same file limits as for supplier files apply (NFR-4).

**Notes:** Not part of the Core minimum. Core runs on seed data and single-job creation (FR-1).

### 4.2 Supplier File Generation

**Description:** When the supplier's jobs are entered, the production planner clicks **Generate supplier file** for one supplier. There is no separate "ready" or "finalize" step. PTS creates a `.xlsx` file from the fixed template with all of that supplier's open jobs sorted by room, stores the export with every value it contained, and downloads the file. The planner sends it outside PTS, by email or a shared folder. The draft template is `pts-supplier-template.xlsx` in this folder. Realizes UJ-1, UJ-3.

**Functional Requirements:**

#### FR-6: Generate a supplier file

**Priority: Core.** The production planner can generate a supplier file for one supplier. Realizes UJ-1.

**Consequences (testable):**
- The file contains one row per open job of that supplier, and no jobs of other suppliers.
- Rows are sorted by room, then by drawing number.
- Every row carries the same Export ID, which is unique to this export, and the export date.
- The export stores every value of every row, so later checks (W10, W13, W14, W15 and FR-15a) can compare against it.
- Generating a file for a supplier with no open jobs shows a message, and no file or export is created.

#### FR-7: Fixed template

**Priority: Core.** The supplier file follows the fixed template, in Norwegian (§3.1).

**Consequences (testable):**
- **Locked columns, in this order:** Export ID, Export date, Job ID, Room, Drawing number, Revision, Revision note, Supplier, Due date.
- **Editable columns, in this order:** Material, Welded, Inspected, Blasted, Painted, Final inspection, Stopped, Stop reason, Expected delivery date, Comment / issue description.
- Column headers, allowed values and sheet names use the Norwegian labels in §3.1.
- Locked columns are protected and grey. Editable columns are unlocked and yellow. Sheet protection has no password.
- The file has an instructions sheet in Norwegian, explaining how to fill in the file and the rules from §4.3.
- Dates are shown as `dd.mm.yyyy`.
- The area, the delivery date and internal-only information are not included.

#### FR-8: Pre-filled current values

**Priority: Core.** The editable columns are pre-filled with the job's current supplier-reported values.

**Consequences (testable):**
- For a job with *Material* 18.11.2026 and *Sveiset* 20.11.2026, the exported row shows both dates and empty cells for the later stages.
- On import, an editable cell whose value equals its exported value is not a supplier-changed cell, and it is never applied, whatever the job data is now.

#### FR-9: Dropdowns and cell validation

**Priority: Core.** The editable columns guide the supplier towards valid values.

**Consequences (testable):**
- Stopped and Stop reason are dropdown lists containing exactly the allowed values in Norwegian.
- The stage columns and Expected delivery date accept only dates.
- Missing conditional fields are highlighted, for example *Stoppet* = *Ja* without a reason.
- PTS does not rely on these in-file checks. Every rule is checked again on import (§4.3).

#### FR-10: New revision in the file and clearing the mark

**Priority: Core.** Jobs with a new-revision mark are marked in the supplier file, and the export clears the mark. Realizes UJ-3.

**Consequences (testable):**
- A job with a new-revision mark has its Revision cell highlighted, and Revision note says `NY REVISJON`. Otherwise Revision note is empty.
- After the file is generated, the new-revision mark of every job in the file is cleared.
- Generating a file for another supplier does not clear the mark.

### 4.3 Import and Validation

**Description:** The production planner uploads a returned supplier file. PTS first runs the file checks. If one fails, the file is rejected with a message, and no import is created. Otherwise PTS checks every row, creates a pending import and shows its change view. Nothing is written to job data at this stage. Rule IDs are those of the brief. Realizes UJ-2, UJ-5, UJ-6.

**Functional Requirements:**

#### FR-11: Upload a supplier file

**Priority: Core.** The production planner can upload a supplier file. Realizes UJ-2.

**Consequences (testable):**
- PTS reads the Export ID from the file and finds the export and supplier from it. The planner does not select them.
- Uploading creates a pending import or shows a file rejection message, within the limits in NFR-4 and NFR-5.
- In Core a supplier has at most one pending import. Uploading a second file while one is pending is refused with a message that says to approve or reject the first. FR-19 replaces this in the Extension.

#### FR-12: File checks (F1–F5)

**Priority: Core.** The whole file is rejected (a file rejection), and no import is created, when:

- **F1** — the file is not an `.xlsx` file, or cannot be read.
- **F2** — one or more template columns are missing or renamed.
- **F3** — the Export ID is missing, was not generated by PTS, or differs between rows.
- **F4** — the file contains no job rows.
- **F5** — the Export ID belongs to an earlier export than the latest export for that supplier. Once FR-19 is built, such a file is accepted and gets warning W9 instead.

**Consequences (testable):**
- The message names the rule and the problem, for example: «F2: Kolonnen *Sveiset* mangler».
- File rejections are shown but not stored in the import log (§7.2).

#### FR-13: Row rejection rules (R1–R7)

**Priority: Core.** A row is rejected, and never applied, when:

- **R1** — *Stoppet* is not *Ja*, *Nei* or empty, or the stop reason is not an allowed value (NFR-10).
- **R2** — *Stoppet* is *Ja* without a stop reason, or the reason is *Annet* without a comment.
- **R3** — retired. The ID is not reused.
- **R4** — retired. The ID is not reused.
- **R5** — a stage date or the expected delivery date is not a valid date.
- **R6** — the Job ID does not exist in PTS, or the job belongs to a different supplier than the export.
- **R7** — the same Job ID appears more than once in the file. All rows with that Job ID are rejected.

**Consequences (testable):**
- Each rejected row shows the Job ID, the rule ID and a message, for example: «R2: Stoppet er Ja, men årsak til stopp mangler».
- A row breaking several rules lists all of them.
- An empty stage date means the stage is not completed. An empty expected delivery date means "not given". Empty *Stoppet* means *Nei*.
- For R5, PTS accepts real Excel dates and dates written as text in `dd.mm.yyyy` or `yyyy-mm-dd`. Any other text is rejected.

#### FR-14a: Core warning rules (W8, W10, W11)

**Priority: Core.** A row gets a warning when one of the conditions below holds. Warnings do not stop approval.

- **W8 Revision mismatch** — the revision in the file differs from the job's current revision.
- **W10 Unexpected change** — a value in a locked column differs from its exported value. Locked-column values are never applied.
- **W11 Delay** — the expected delivery date is later than the due date.

**Consequences (testable):**
- Each warning shows its rule ID and a Norwegian message naming the values involved, for example: «W11: Forventet dato levert 09.12.2026 er etter fristen 27.11.2026».

#### FR-14b: Extension warning rules (W9, W12–W15)

**Priority: Extension.** A row, or the whole import for W9, gets a warning when one of the conditions below holds. Warnings do not stop approval.

- **W9 Outdated file** — a newer export exists for the same supplier. Applies to the whole import and is checked whenever the import is shown. It replaces file check F5 once FR-19 is built.
- **W12 Stage out of order, or date removed** — in the row as it would look after the import, a stage has a date while an earlier stage has none, or the file removes a stage date the job has in PTS.
- **W13 Missing job** — an open job that was in the export is missing from the file. The job is left unchanged.
- **W14 Job changed by another import** and **W15 Conflict with manual update** — one rule for both. A field gets a warning when the job changed after the export (D ≠ E) and the file value differs from the current value (F ≠ D). The cause decides the ID: **W14** if the latest change after the export came from another approved import, **W15** if it came from a manual update (FR-28). Warnings are shown per field. FR-15a defines what happens to the value in each case, and FR-15b how the planner decides.

**Consequences (testable):**
- Each warning shows its rule ID and a Norwegian message naming the values involved, for example: «W15: PTS har *20.11.2026* (manuell oppdatering 23.11.2026, Ingrid), fila har *21.11.2026*».
- W14 and W15 are shown per field, so the planner sees which field is in conflict.
- W14 and W15 can only occur once manual updates (FR-28) or several pending imports (FR-19) exist.
- Scenario tests for W14 and W15 use the cases in FR-15a with concrete values (FR-27).

#### FR-15a: Change view

**Priority: Core.** For each pending import, the production planner sees what would change on approval. Realizes UJ-2, UJ-5.

**Consequences (testable):**
- **Per job:** each supplier-changed cell, with the value in PTS now and the value in the file.
- Each supplier-reported field of each row falls into one of five cases. E is the exported value, D the current value and F the file value:

| Case | D vs E | F | What happens |
|---|---|---|---|
| 1 | D = E | F = E | No change. |
| 2 | D = E | F ≠ E | The file value is applied. |
| 3 | D ≠ E | F = E | The PTS value is kept (*kept*). The supplier did not touch the cell. W14 or W15 is shown as information, and no choice is needed. |
| 4 | D ≠ E | F ≠ E and F ≠ D | **Conflict field.** W14 or W15 is shown, and the planner must choose *Use file value* or *Keep PTS value* (FR-15b). |
| 5 | D ≠ E | F = D | Nothing to apply, and no warning. |

- Example for case 3: E = empty, D = 20.11.2026 (manual update), F = empty. The result is *kept 20.11.2026* with W15.
- Example for case 4: the same E and D, with F = 21.11.2026. The planner chooses between 20.11.2026 and 21.11.2026.
- Jobs with no supplier-changed cells are listed as *No change* (*Ingen endring*).
- Rejected rows and warnings are listed with rule IDs and can be filtered.
- A summary at the top shows the number of changed jobs, unchanged jobs, rejected rows and warnings.
- Opening the change view never changes job data.

**Notes:** A low-fidelity sketch is in `addendum.md` §A3.3, and the screen list in §A3.1. UX refines the layout. In Core only cases 1 and 2 occur, because a supplier has one pending import and F5 only accepts the latest export (FR-11, FR-12). Cases 3–5 are defined here so the rule is written in one place, and they are built with FR-14b and FR-15b.

#### FR-15b: Conflict fields and the planner's choice

**Priority: Extension.** The production planner decides every conflict field (case 4 in FR-15a). Realizes UJ-5, UJ-6.

**Consequences (testable):**
- Conflict fields are listed at the top of the change view and are never collapsed. Each shows both values and the cause: who and when for W15, or which import for W14. No choice is preselected.
- Cells in case 3 are shown as *kept*, with W14 or W15 as information and no choice.
- The summary at the top also shows the number of unresolved conflict fields, and the list of pending imports shows it per import (FR-19).
- **Approve** is disabled while any conflict field has no choice, and shows how many remain. A conflict field with *Use file value* is applied, and one with *Keep PTS value* is left unchanged.
- The choice is recorded in the import log (FR-21). *Keep PTS value* is not a change, so it is not in the job history.
- A choice is reset when the PTS value changes again before approval (FR-20).

**Notes:** This replaces the v1 rule that a supplier-changed cell wins over a manual update. The planner can still reject the whole import.

#### FR-16: Revision reported per import

**Priority: Core.** For each import, PTS stores the revision each row reported.

**Consequences (testable):**
- The import log shows the reported revision per row, even after the job's current revision has changed.

#### FR-30: The stop reason follows *Stoppet*

**Priority: Core.** The stop reason is stored only together with *Stoppet* = *Ja*.

**Consequences (testable):**
- When an approved import or a manual update sets *Stoppet* to *Nei*, the job's stop reason is cleared.
- A file row with a stop reason but *Stoppet* = *Nei* is not rejected. The reason is ignored, and the change view says so.
- The comment is kept regardless of *Stoppet*.

### 4.4 Approval and Import Log

**Description:** The production planner approves or rejects a pending import as a whole. Approval applies all supplier-changed cells of non-rejected rows in one operation. Once conflict fields exist (FR-15b), the planner's choice for each one decides its value. In Core a supplier has one pending import at a time, and several can exist once FR-19 is built. Every decision is logged. Realizes UJ-2, UJ-5, UJ-6.

**Functional Requirements:**

#### FR-17: No change before approval

**Priority: Core.** Job data is never changed by uploading, validating or viewing an import.

**Consequences (testable):**
- Automated tests show that job data is identical before and after uploading, validating and viewing the change view, for every example file.

#### FR-18: Approve or reject a whole import

**Priority: Core.** The production planner can approve or reject a pending import. Realizes UJ-2.

**Consequences (testable):**
- **Approve:** all supplier-changed cells of non-rejected rows are applied in one all-or-nothing operation. If anything fails, nothing is applied.
- **Reject:** nothing is applied.
- Rejected rows are never applied, even when the import is approved.
- Cells that are not supplier-changed are never applied (FR-8).
- Every applied change is recorded in the job history (FR-5), linked to the import log entry. FR-18 owns writing job history for imports, FR-28 for manual updates, and FR-29a and FR-29b for deliveries, closes and reopens.
- An approved or rejected import cannot be decided again.
- Individual rows cannot be approved or rejected (§7.2). Conflict fields are decided one by one (FR-15b).

#### FR-19: Several pending imports

**Priority: Extension.** Several pending imports may exist at once, even for the same supplier and the same jobs. Realizes UJ-6.

**Consequences (testable):**
- Uploading a second file for a supplier with a pending import succeeds and creates a second pending import.
- The list of pending imports shows supplier, Export ID, file name, upload time and the number of unresolved conflict fields.
- A file from an earlier export is accepted with W9, and file check F5 no longer applies.

#### FR-20: Always current

**Priority: Extension.** The validation result and change view of a pending import always reflect the current job data. Realizes UJ-6.

**Notes:** The principle at the start of §4 holds in Core too: edits through FR-2 and FR-3 show up in the pending import (see FR-2 and FR-3). FR-20 adds what is needed once several imports can be pending.

**Consequences (testable):**
- After another import is approved, the change view of every other pending import shows the updated values in the PTS column.
- A choice made on a conflict field is reset when the PTS value changes again before approval.
- W14 appears on another pending import after an approval only for fields that fit the conflict rule in FR-14b.

#### FR-21: Import log

**Priority: Core.** Every approved or rejected import is logged.

**Consequences (testable):**
- Each entry has date and time, file name, Export ID, supplier, user name, result (*Godkjent* / *Avvist*), and counts of changed jobs, rejected rows and warnings.
- From an entry, the planner can see the change view as it was when the import was decided, including the revision each row reported (FR-16) and, once FR-15b is built, the choice made for each conflict field.
- Log entries cannot be edited or deleted in the app.

#### FR-22: Fixed user name

**Priority: Core.** With no login in v1, PTS records a configured user name on every approval, rejection, manual update, delivery, close and reopen.

**Consequences (testable):**
- The user name is set in configuration, with a default for the demo, for example "Planlegger (demo)".
- The import log and the job history show it.

### 4.5 Dashboard

**Description:** The dashboard is the production planner's starting point. It lists jobs with their key fields and flags, and lets the planner find everything that needs action in a few clicks. Realizes UJ-4.

**Functional Requirements:**

#### FR-23: Job overview

**Priority: Core.** The dashboard lists jobs with these fields:

- Job ID
- drawing number and current revision
- room and area
- supplier
- active stage, and the six stage dates
- stopped and stop reason
- due date and expected delivery date
- comment / issue description
- last export date
- flags (FR-24)

**Consequences (testable):**
- A newly created job appears with all these fields.
- Jobs can be sorted by due date and filtered by supplier, room and area.

#### FR-24: Flags

**Priority: Core.** Each job shows the flags that apply:

- **Stopped** — with the reason.
- **Ready for inspection** — the active stage is Inspected or Final inspection.
- **Delayed** — expected delivery date later than due date.
- **New revision — send updated file to supplier** — the job has a new-revision mark.
- **Revision mismatch flag** — an approved import reported a revision other than the one that was current for the job when the import was approved. Rejected rows do not count. The flag is cleared when a later approved import reports the current revision, or when the planner registers a new revision (the new-revision mark then takes over).
- **Has comment** — the comment / issue description is not empty.

**Consequences (testable):**
- A job with expected delivery date 09.12.2026 and due date 27.11.2026 shows *Delayed*.
- The *New revision* flag disappears when a supplier file containing the job is generated.
- Registering a new revision does not raise the *Revision mismatch flag* on its own.
- **Scenario:** a file reports revision B while the current revision is C, and the import is approved: the flag is set. The planner then registers revision D: the flag is cleared and the new-revision mark is set.
- A job with *Material*, *Sveiset* and *Kontrollert* filled in and the later stages empty has the active stage *Sandblåst*. A job with *Material* and *Sveiset* filled in and *Kontrollert* empty has the active stage *Kontrollert* and is *Ready for inspection*.
- A job with *Sveiset* filled in but *Material* empty has the active stage *Material*.

#### FR-25: Action filters

**Priority: Core.** The production planner can filter the dashboard to jobs that are stopped, ready for inspection, delayed, or affected by a new revision (new revision or revision mismatch flag). Realizes UJ-4.

**Consequences (testable):**
- Each filter shows exactly the jobs with that flag and no others.
- The number of jobs per filter is visible without applying the filter.
- By default, only open jobs are shown, with an option to include closed jobs.

## 5. Cross-Cutting Non-Functional Requirements

- **NFR-1 Data integrity.** Job data changes only through:
  - the job register: FR-1, FR-2, FR-3, FR-28, FR-29a, FR-29b and FR-31
  - generating a supplier file, which clears new-revision marks (FR-10)
  - an approved import (FR-18), which is all-or-nothing
- **NFR-2 Traceability.** Every change to supplier-reported fields, and every delivery, close and reopen, can be traced through the job history to one import log entry or one planner action (manual update, delivery, close or reopen).
- **NFR-3 Runnable locally.** PTS runs on a single developer machine by following the README. It needs no paid services, no external accounts and no personal API keys or credentials. The README covers:
  - install
  - starting the app
  - seeding and resetting (FR-26)
  - running the tests
  - trying UJ-1 and UJ-2 with the example files
- **NFR-4 Safe file handling.**
  - Only `.xlsx` files are accepted. Macro-enabled files (`.xlsm`) are rejected by F1.
  - Uploads are limited to 5 MB.
  - File content is only read as data and is never executed.
  - Uploaded files are kept as long as their import and log entry need them.
- **NFR-5 Responsiveness.** Validating a supplier file of up to 500 rows and showing its change view takes under 5 seconds on a typical laptop.
- **NFR-6 Understandable messages.** Every rejection and warning names its rule ID and says in plain Norwegian what is wrong and, where possible, what the values were.
- **NFR-7 Testability.** Automated tests cover every validation rule in use (F1–F5, R1, R2, R5–R7, W8–W15), FR-17 and the approval rules in FR-18.
- **NFR-8 Fictional data only.** No real company data, drawings, project names or supplier names in the repository, seed data, example files, documentation or code. The real-world case involves classified documentation.
- **NFR-9 Platform.** A desktop web application, used in a current version of Chrome or Edge. Mobile is not supported in v1.
- **NFR-10 Language.** Everything a user or supplier sees is in Norwegian, using the labels in §3.1. This covers the user interface, messages, the supplier file and the rule messages.
  - Stored values (stop reason) use the English Glossary terms internally and are shown with their Norwegian labels.
  - On import, the Norwegian values in the file are mapped to the stored values. A value with no mapping fails R1.
  - Dates are shown as `dd.mm.yyyy` everywhere.
  - Rule IDs (F1, R2, W15 …) are the same in every language.
  - The example messages in this PRD show content, not final wording.
  - The PRD, code and documentation are in English (project rule).
- **NFR-11 Repository hygiene.** The local database, uploaded files and generated supplier files are excluded from git. The app needs no secrets. Configuration, such as the user name in FR-22, has a committed example file with safe defaults. Example files and seed data live in `testdata/`.

## 6. Non-Goals (Explicit)

- PTS does not replace ERP, PDM, PLM, MES or quality systems, and is not a system of record for engineering or finance.
- PTS does not store engineering drawings as the authoritative source.
- PTS does not send email or integrate with shared folders. File transfer is manual.
- PTS does not give suppliers access to internal systems.
- PTS does not approve technical or quality decisions automatically.
- PTS does not become a warehouse, logistics or financial system.
- PTS does not plan production. It tracks status.

## 7. MVP Scope

### 7.1 In Scope (v1), by Priority

**Core** — the flow that must be finished and stable first: create job → generate supplier file → import → change view → approve → dashboard. In Core a supplier has one pending import at a time and only files from its latest export are accepted (FR-11, FR-12), so no conflicts occur.

**Core minimum** — the first slice, the smallest flow that works end to end (20 requirements). Built in this order:

1. Job register: create, new revision, job detail (FR-1, FR-3, FR-5)
2. Supplier file: generate, fixed Norwegian template, pre-filled values, dropdowns, new-revision marking (FR-6 … FR-10)
3. Import: upload, file checks, row rules, warnings W8, W10 and W11, change view (FR-11, FR-12, FR-13, FR-14a, FR-15a)
4. Approval: no change before approval, approve/reject, import log, user name (FR-17, FR-18, FR-21, FR-22)
5. Dashboard and demo data: overview, flags, seed data (FR-23, FR-24, FR-26)

**Rest of Core** — after the minimum (6 requirements): edit a job (FR-2), reported revision (FR-16), stop reason follows *Stoppet* (FR-30), action filters (FR-25), register delivery (FR-29a), example files for Core rules (FR-27).

**Extension** — built after Core is stable (8 requirements), in this order:

1. Conflict handling: manual update (FR-28), warnings W9, W12, W13, W14 and W15 (FR-14b), conflict fields and the planner's choice (FR-15b), several pending imports (FR-19), always current (FR-20)
2. Import a job package (FR-31)
3. Close and reopen by hand (FR-29b)
4. Supplier management (FR-4)

### 7.2 Out of Scope for v1

- Recording inspection results, delivery details, internal assembly and final approval. Only the dates the supplier completes Inspected and Final inspection are tracked. Results are deferred to later versions to protect the core flow this semester.
- Several internal users, roles and login (Windows / Microsoft Entra ID). Later versions.
- Revision history. PTS stores only the current revision.
- Approving or rejecting individual rows in an import. Choices are made only for conflict fields.
- Automatic notification of the project manager and job owner on revision changes. Later versions.
- History of edits made through FR-2 and FR-3. Only supplier-reported fields, deliveries, closes and reopens are recorded in the job history.
- Logging of file rejections and of job package imports. They are shown but not stored.
- Deleting jobs or suppliers. Jobs are closed instead (FR-29a, FR-29b).
- A customer or order field on jobs, for the same drawing produced for different customers. Later versions.

## 8. Success Metrics

The v1 success criteria are functional and checked by tests and a demo run. SM-1 … SM-12 correspond to success criteria 1–12 in the brief.

**Primary**
- **SM-1** — A created job appears on the dashboard with all fields in FR-23. Validates FR-1, FR-23.
- **SM-2** — A supplier file contains only that supplier's open jobs, sorted by room, with a unique Export ID and each job's current revision. Validates FR-6, FR-7.
- **SM-3** — Every rejected row is shown with an understandable message naming the broken rule. Validates FR-13, NFR-6.
- **SM-4** — Before approval, the change view shows exactly which cells change per job. Validates FR-15a.
- **SM-5** — No import changes job data before it is approved, verified by tests. Validates FR-17.
- **SM-6** — A file reporting an older revision is flagged with warning W8. Validates FR-14a (W8).
- **SM-7** — A job whose expected delivery date is later than its due date is flagged as delayed. Validates FR-24.
- **SM-8** (Extension) — When two pending imports share a job and one is approved, the other shows the updated values, and a conflict field with W14 where it would overwrite them. The planner chooses per field. Validates FR-19, FR-20, FR-14b (W14), FR-15b.
- **SM-9** — From the dashboard alone, the planner finds all jobs that are stopped, ready for inspection, delayed, or affected by a new revision. Validates FR-25.
- **SM-10** — Stopped and stop reason are dropdowns with only the allowed values, and the stage columns accept only dates. Validates FR-9.
- **SM-11** — A new revision is marked on the dashboard and in the next supplier file, and the *New revision* flag disappears after export. Validates FR-3, FR-10, FR-24.
- **SM-12** — A file that is not a valid PTS supplier file is rejected as a whole with a clear message. Validates FR-12.

**Secondary**
- **SM-13** — Every example file produces its expected result per row in the automated tests. Validates FR-27, NFR-7.
- **SM-14** — The examiner can run PTS and complete UJ-1 and UJ-2 from the README alone. Validates NFR-3, FR-26.
- **SM-15** (Extension) — A file that disagrees with a manual update made after the export shows W15. An untouched cell never overwrites the newer value, and a changed cell is applied only after the planner chooses the file value. Validates FR-28, FR-14b (W15), FR-15a, FR-15b, FR-8.
- **SM-16** — Every change to supplier-reported fields appears in the job history, linked to an import log entry or a planner action. Validates FR-5, FR-21, NFR-2.

**Counter-metrics (guards, checked in UX review and tests)**
- **SM-C1** — Warnings are never hidden or collapsed by default in the change view, and no setting turns a warning off. Counterbalances SM-3 and SM-4.
- **SM-C2** — **Approve import** is never the default or pre-focused action, and approval always needs a deliberate click on the change view. No choice for a conflict field is preselected, and approval is disabled until every conflict field has a choice. Counterbalances SM-4 and SM-5.
