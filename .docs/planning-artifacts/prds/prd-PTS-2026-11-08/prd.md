**How to read it:**

- **Glossary.** Every domain term is defined once in §3 and used verbatim everywhere else.
- **Requirement IDs.** Features (§4) carry globally numbered requirements, FR-1 … FR-30. IDs are stable and never renumbered. FRs are grouped by feature, so numbers are not always in order: FR-28 and FR-29 sit in §4.1, and FR-30 in §4.3. A range such as "FR-11 … FR-16" means those numbers only.
- **Traceability.** The "Realized by" line of each user journey is the complete journey-to-FR mapping. "Realizes UJ-N" notes on FRs are shortcuts for the main journeys.
- **Rule IDs.** Validation rules keep the IDs from the brief: F1–F4, R1–R7 and W8–W15. The same rule has the same ID in the brief, this PRD, the stories and the tests.
- **Priority.** Every FR has a priority, **Core** or **Extension** (§7.1). Core is the flow that must be finished and stable first: *create job → generate supplier file → import → change view → approve → dashboard*.
- **Success metrics.** SM-1 … SM-12 correspond one-to-one to success criteria 1–12 in the brief. SM-13 … SM-16 and the counter-metrics SM-C1 and SM-C2 are added by this PRD.
- **Assumptions.** Inferences not yet confirmed are tagged `[ASSUMPTION]` inline and listed in §11.
- **Addendum.** Technical hints, template build details and screen sketches live in `addendum.md`.

## 1. Vision

PTS is an internal web application that gives a production planner one reliable overview of production jobs placed with external suppliers. It answers one question quickly: *"Where is this job, and is there anything we need to act on?"*

Suppliers never get access to the company's systems. Instead, PTS generates a controlled Excel file per supplier with the same fields the planner sees in the app. The supplier fills in production status, completed quantity, expected completion date and any issues, and returns the file. PTS checks every row, shows exactly what would change, and updates the job data only when the planner approves.

The value is trust in the data. Today, status lives in scattered Excel files and emails, and it is hard to know which version is current. PTS does three things:

- it makes the database the single current picture
- it makes every change traceable to an approved import or a recorded manual update
- it makes problems visible early: jobs on hold, inspection requests, delays, and suppliers working from an outdated drawing revision

### 1.1 Long-Term Direction

v1 covers the supplier part of a longer flow. The long-term direction is a tracking system that follows a job from start to finish:

**Engineering → Supplier Production → Inspection → Delivery → Internal Assembly → Final Approval**

The capabilities deferred from v1 are listed in §7.2. One more later step: measuring business effects once baseline numbers are available, such as less time spent on manual follow-up and fewer errors from outdated revisions.

PTS should stay simple and focused, and should not duplicate ERP, PDM or quality systems.

## 2. Target User

### 2.1 Jobs To Be Done

- **Functional:** know the current status of every job at every supplier without phoning or emailing around.
- **Functional:** send a supplier a clear, up-to-date list of their jobs and get structured updates back.
- **Functional:** record what a supplier says on the phone, and be warned when a later file disagrees.
- **Functional:** catch problems early: a job on hold, a request for inspection, a delay, or a supplier still working from an old drawing revision.
- **Contextual:** work within a controlled IT environment where suppliers cannot access internal systems, and file transfer happens by email or a shared folder.
- **Emotional:** be confident that nothing in the job data changed without the planner seeing it.

### 2.2 Users in v1

- **Production planner** — the one internal role in v1. Creates jobs, generates supplier files, imports returned files, approves or rejects imports, records manual updates, registers new drawing revisions and follows up from the dashboard.
- **Supplier** — an indirect user. Never uses PTS. Only receives and returns the supplier file.

### 2.3 Non-Users (v1)

- Project, engineering, quality and inspection personnel as separate roles (later versions).
- Suppliers as direct users of PTS.

### 2.4 Key User Journeys

The persona is fictional: **Ingrid, production planner** at a marine engineering company, responsible for about 40 open jobs across five machining and welding suppliers. Screen labels are shown in English with the Norwegian label in italics where it helps. Terms such as *pending import*, *change view* and *supplier-changed cell* are defined in §3, and rule IDs (W8, W15 …) in §4.3.

**UJ-1. Ingrid registers new jobs and sends Leverandør Alfa their file.**
- **Entry state:** PTS is open in the browser on her desktop. There is no login in v1.
- **Path:**
  1. She creates three new jobs for Leverandør Alfa, entering drawing number, revision, description, quantity, supplier and due date for each.
  2. She opens Leverandør Alfa and clicks **Generate supplier file** (*Lag leverandørfil*).
  3. PTS downloads an `.xlsx` file. It holds all of Leverandør Alfa's open jobs, a unique Export ID and the current values pre-filled.
  4. She attaches the file to an email to the supplier, outside PTS.
- **Climax:** the file opens in Excel with locked grey columns, yellow editable columns and dropdown lists in Norwegian. She knows the supplier cannot pick an invalid status.
- **Resolution:** the export is recorded, and the dashboard shows the date each job was last sent. Jobs with a new-revision mark lose the mark, because the supplier now has the updated file.
- Realized by FR-1, FR-6 … FR-10, FR-23.

**UJ-2. Ingrid imports Leverandør Alfa's returned file and approves it.**
- **Entry state:** Leverandør Alfa has emailed the file back. Ingrid saves it locally.
- **Path:**
  1. She opens **Import supplier file** (*Importer leverandørfil*) and uploads the file.
  2. PTS checks the file as a whole, then every row, and creates a pending import.
  3. The change view shows, per job, the cells the supplier changed (value in PTS → value in file), which rows are rejected and why, and which rows carry warnings.
  4. She sees that PTS-0003 is now *Stoppet — Mangler materiale*, and that PTS-0002 reports revision B while the current revision is C.
  5. She clicks **Approve import** (*Godkjenn import*).
- **Climax:** the dashboard immediately shows PTS-0003 as on hold and PTS-0002 with a revision mismatch. She knows exactly what changed, because she saw every change on one screen before approving.
- **Resolution:** the import is in the import log with date, file name, user and result. She phones the supplier about the outdated drawing.
- **Edge cases:**
  - The file is not a PTS supplier file (wrong columns, no Export ID). PTS rejects the whole file with a clear message, and no pending import is created.
  - A row has status *Stoppet* without a reason. That row is rejected and shown with rule R2, and the other rows can still be approved.
- Realized by FR-11 … FR-18, FR-21, FR-22, FR-24.

**UJ-3. Ingrid registers a new drawing revision.**
- **Entry state:** engineering has approved revision C of drawing DRW-10002. Ingrid has placed the drawing in the shared folder and emailed the project manager and job owner, as today.
- **Path:**
  1. She opens job PTS-0002 and changes the current revision from B to C.
  2. The job gets the flag *New revision — send updated file to supplier* on the dashboard.
  3. Next time she generates Leverandør Alfa's file, the Revision cell of PTS-0002 is highlighted and the Revision note says `NY REVISJON`.
- **Climax:** the supplier cannot miss that the drawing has changed, and Ingrid cannot forget to tell them.
- **Resolution:** the flag disappears once the new file has been generated. If a file from an older export still reports revision B and is approved, the job is flagged as a revision mismatch.
- Realized by FR-3, FR-10, FR-14 (W8), FR-24.

**UJ-4. Ingrid follows up in the morning and records a phone call.**
- **Entry state:** start of the working day.
- **Path:**
  1. She opens the dashboard.
  2. She filters on *On hold*, then *Ready for inspection*, then *Delayed*, then *New revision or revision mismatch*.
  3. The supplier phones: the missing material for PTS-0003 has arrived, and work has restarted. Ingrid opens PTS-0003 and records a manual update to *I produksjon*.
- **Climax:** she has a short list of jobs to act on without opening any Excel file, and the phone call is recorded with her name in the job history.
- **Resolution:** she books an inspection before painting for PTS-0004 and follows up the delayed jobs.
- Realized by FR-5, FR-23 … FR-25, FR-28.

**UJ-5. A returned file disagrees with the phone call.**
- **Entry state:** after the call in UJ-4, Leverandør Alfa returns the file Ingrid sent last week. PTS-0003 still shows *Stoppet*, because the supplier forgot to update that row.
- **Path:**
  1. Ingrid uploads the file.
  2. The change view flags PTS-0003 with **W15 Conflict with manual update**. The file says *Stoppet* (unchanged since the export), and PTS says *I produksjon* (manual update, 10.11.2026, Ingrid).
  3. Because the supplier did not change that cell, PTS will keep *I produksjon*. The other rows show normal changes.
  4. Ingrid phones the supplier, who confirms that work has restarted, and she approves the import.
- **Climax:** the conflict was impossible to miss, and approving the file did not undo the phone call.
- **Edge case:** if the supplier *had* changed the cell, for example to *Ferdig*, W15 would still be shown and the file value would win on approval. If Ingrid is unsure, she rejects the import and asks for a new file.
- Realized by FR-8, FR-14 (W15), FR-15, FR-18, FR-28.

**UJ-6. Two returned files from the same supplier wait at the same time.**
- **Entry state:** Leverandør Alfa returned Monday's file, from export 1, which is still pending. On Tuesday they return a file from a newer export 2.
- **Path:**
  1. Ingrid uploads Tuesday's file. PTS accepts it as a second pending import. Monday's import now carries W9 *Outdated file*.
  2. She approves Tuesday's import first.
  3. Monday's import is recalculated against the updated job data. Rows where Monday's file changed a field that Tuesday's import has since changed get W14 *Job changed by another import*.
- **Climax:** she sees that approving Monday's file would overwrite Tuesday's newer values, and rejects it.
- **Resolution:** both decisions are in the import log.
- Realized by FR-14 (W9, W14), FR-19, FR-20, FR-21.

## 3. Glossary

**Jobs and revisions**

- **Job** — one production order placed with one supplier for one drawing. Has a Job ID, drawing number, current revision, description, quantity, supplier, due date and supplier-reported fields. Belongs to exactly one supplier.
- **Job ID** — unique identifier of a job, generated by PTS (e.g. `PTS-0001`). `[ASSUMPTION]`
- **Supplier** — an external workshop that produces jobs. Has a unique name and zero or more jobs.
- **Drawing number** — identifier of the engineering drawing the job is produced from. The drawing itself lives outside PTS.
- **Current revision** — the drawing revision the job must be produced to, as registered in PTS. PTS stores only the current revision, not a history.
- **New-revision mark** — a flag on a job. It is set when the production planner changes the job's current revision, and cleared when a supplier file containing the job is generated.
- **Open job** — a job that is not closed. Only open jobs are included in supplier files.
- **Closed job** — a job that is not open. It closes automatically on `Completed`, or by hand. FR-29 specifies closing and reopening.
- **Production status** — one of `Not started`, `In production`, `On hold`, `Ready for inspection`, `Completed`. A new job is `Not started`, which covers both "not yet sent" and "sent, work not started". Whether a job has been sent is shown by its last export date.
- **On hold reason** — one of `Drawing issue`, `Missing material`, `Check requested`, `Other`. Required when the production status is `On hold`.
- **Inspection request** — a supplier's request for inspection, given by production status `Ready for inspection` plus an inspection type: `Before painting` or `Final`.
- **Supplier-reported fields** — production status, on hold reason, inspection type, completed quantity, expected completion date and comment. The only fields an import or a manual update may change.

**Supplier file and export**

- **Supplier file** — the `.xlsx` file PTS generates for one supplier, following the fixed template, with locked columns and editable columns.
- **Export** — the stored record that a supplier file was generated: Export ID, export date, supplier, and every job and value the file contained.
- **Export ID** — unique identifier of one export, printed in every row of the supplier file.
- **Exported value** — the value a cell had in the supplier file when it was generated, as stored in the export.
- **Supplier-changed cell** — an editable cell whose value in the returned file differs from its exported value. Only supplier-changed cells are applied on approval.

**Import and validation**

- **Import** — one uploaded supplier file, together with its validation result and change view. Has a state: `Pending`, `Approved` or `Rejected`.
- **Pending import** — an import waiting for the production planner to approve or reject it. Several can exist at once, also for the same supplier.
- **File check** — a check on the uploaded file as a whole (rules F1–F4). A failed file check rejects the file, and no import is created.
- **Rejected row** — a row in an import that broke a rejection rule (R1–R7). Never applied.
- **Warning** — a flag on a row or an import that does not stop it (W8–W15). Shown to the production planner before approval.
- **Change view** — the screen showing, for one import, which supplier-changed cells would be applied (value in PTS → value in file), plus rejected rows and warnings.
- **Approve / Reject** — the production planner's decision on a whole import.

**Records**

- **Import log** — the permanent record of every approved or rejected import.
- **Manual update** — a change the production planner makes by hand to a job's supplier-reported fields, for example after a phone call with the supplier.
- **Job history** — the permanent record, per job, of every change to its supplier-reported fields and every close or reopen. Each entry is linked to an import log entry or a manual update.

**Screens and flags**

- **Job register** — the screens where the production planner creates and edits jobs and sees a single job in detail, including its flags and job history. The dashboard is the overview across jobs.
- **Dashboard** — the main overview of jobs, with flags and filters.
- **Delayed** — a job whose expected completion date is later than its due date.
- **Revision mismatch** — a returned supplier file reports a revision other than the job's current revision (warning W8). A job keeps the *Revision mismatch* flag as defined in FR-24.

## 4. Features

**Principle for all of §4:** validation results and the change view of every pending import are always computed against the current job data. Any change to a job therefore shows up in every pending import that contains it: an approved import, a manual update, or an edit in the job register.

### 4.1 Job Register

**Description:** The production planner creates, views and edits jobs, records manual updates, closes and reopens jobs, and manages suppliers. The job fields in the app are the same as the columns in the supplier file, so what the planner sees and what the supplier sees match. UX decides whether the register is a spreadsheet-like table or a table with a separate form (§10). Supplier-reported fields change through an approved import or a manual update, and both are recorded in the job history. Realizes UJ-1, UJ-3, UJ-4.

**Functional Requirements:**

#### FR-1: Create a job

**Priority: Core.** The production planner can create a job with drawing number, revision, description, quantity, supplier and due date. Realizes UJ-1.

**Consequences (testable):**
- All six fields are required. Saving without one shows which field is missing.
- Quantity must be a whole number of 1 or more.
- Due date must be a valid date.
- PTS assigns a unique Job ID.
- A new job is an open job with production status `Not started` and completed quantity 0, and it appears on the dashboard immediately.

#### FR-2: Edit a job

**Priority: Core.** The production planner can edit drawing number, description, quantity, supplier and due date of a job.

**Consequences (testable):**
- Supplier-reported fields are changed through FR-28, not through this form.
- Quantity cannot be set below the job's current completed quantity.
- Changing the supplier of a job that is in a pending import makes its rows in that import fail R6.
- Edits through FR-2 are not recorded in the job history (§7.2).

#### FR-3: Register a new revision

**Priority: Core.** The production planner can change the current revision of a job. Realizes UJ-3.

**Consequences (testable):**
- After saving a different revision, the job has a new-revision mark.
- Saving the same revision again does not set a new-revision mark.
- The previous revision is not stored on the job. Earlier imports in the import log keep the revision they reported (FR-16).

#### FR-4: Manage suppliers

**Priority: Extension.** The production planner can create a supplier with a name, rename it, and see the list of suppliers. `[ASSUMPTION]`

**Consequences (testable):**
- Supplier names are unique.
- Suppliers cannot be deleted in v1.

**Notes:** Core relies on the suppliers in the seed data (FR-26).

#### FR-5: Job detail

**Priority: Core.** The production planner can open a job and see all its fields, its flags (FR-24), its last export date and its job history. Realizes UJ-4.

**Consequences (testable):**
- The job detail shows every field listed in FR-23.
- The job history lists changes in time order, newest first, each with date and time, user name, source (import or manual update), field, old value and new value.

#### FR-28: Manual update of supplier-reported fields

**Priority: Extension.** The production planner can change a job's supplier-reported fields by hand, as a manual update. Realizes UJ-4, UJ-5.

**Consequences (testable):**
- The same rules as for imported rows apply (R1–R5). A manual update that breaks a rule cannot be saved, and the rule ID and message are shown.
- Every manual update is recorded in the job history with date and time, user name (FR-22), field, old value and new value.
- A pending import whose export was generated before the manual update shows W15 for the affected fields (FR-14).

**Notes:** Accepted risk for v1: a supplier-changed cell wins over a manual update on approval, and W15 is the only guard. The planner rejects the import if in doubt (FR-14, FR-15).

#### FR-29: Close and reopen a job

**Priority: Extension.** A job closes automatically when it reaches `Completed`, and the production planner can close or reopen a job by hand.

**Consequences (testable):**
- **Automatic close:** when an approved import or a manual update sets production status `Completed`, the job becomes a closed job.
- **Manual close:** the production planner can close an open job with any production status. The job history records who closed it and when.
- **Reopen:** the production planner can reopen a closed job. It becomes an open job again and keeps its production status. `[ASSUMPTION]`
- A closed job is not included in the next supplier file (FR-6), and it does not trigger W13.
- A row for a closed job in a returned supplier file is still validated and shown in the change view. `[ASSUMPTION]`

**Notes:** Until FR-29 is built, a job closes only by reaching `Completed`, and a wrongly created job stays open.

### 4.2 Supplier File Generation

**Description:** When the production planner has entered what is needed, they click **Generate supplier file** for one supplier. There is no separate "ready" or "finalize" step. PTS creates a `.xlsx` file from the fixed template with all of that supplier's open jobs, stores the export with every value it contained, and downloads the file. The planner sends it outside PTS, by email or a shared folder. The draft template is `pts-supplier-template.xlsx` in this folder. Realizes UJ-1, UJ-3.

**Functional Requirements:**

#### FR-6: Generate a supplier file

**Priority: Core.** The production planner can generate a supplier file for one supplier. Realizes UJ-1.

**Consequences (testable):**
- The file contains one row per open job of that supplier, and no jobs of other suppliers.
- Every row carries the same, unique Export ID and the export date.
- The export stores every value of every row, so later checks (W10, W13, W15 and FR-15) can compare against it.
- Generating a file for a supplier with no open jobs shows a message, and no file or export is created.

#### FR-7: Fixed template

**Priority: Core.** The supplier file follows the fixed template, in Norwegian (§3.1).

**Consequences (testable):**
- **Locked columns, in this order:** Export ID, Export date, Job ID, Drawing number, Revision, Revision note, Description, Quantity, Supplier, Due date.
- **Editable columns, in this order:** Production status, On hold reason, Inspection type, Completed quantity, Expected completion date, Comment / issue description.
- Column headers, allowed values and sheet names use the Norwegian labels in §3.1.
- Locked columns are protected and grey. Editable columns are unlocked and yellow. Sheet protection has no password. `[ASSUMPTION]`
- The file has an instructions sheet in Norwegian, explaining how to fill in the file and the rules from §4.3.
- Dates are shown as `dd.mm.yyyy`.
- Internal-only information, such as inspection results, is not included.

#### FR-8: Pre-filled current values

**Priority: Core.** The editable columns are pre-filled with the job's current supplier-reported values.

**Consequences (testable):**
- For a job with status `In production` and completed quantity 4, the exported row shows *I produksjon* and 4.
- On import, an editable cell whose value equals its exported value is not a supplier-changed cell, and it is never applied, whatever the job data is now.

#### FR-9: Dropdowns and cell validation

**Priority: Core.** The editable columns guide the supplier towards valid values.

**Consequences (testable):**
- Production status, On hold reason and Inspection type are dropdown lists containing exactly the allowed values in Norwegian.
- Completed quantity accepts only whole numbers from 0 to the row's quantity.
- Expected completion date accepts only dates.
- Missing conditional fields are highlighted, for example *Stoppet* without a reason.
- PTS does not rely on these. Every rule is checked again on import (§4.3).

#### FR-10: New revision in the file and clearing the mark

**Priority: Core.** Jobs with a new-revision mark are marked in the supplier file, and the export clears the mark. Realizes UJ-3.

**Consequences (testable):**
- A job with a new-revision mark has its Revision cell highlighted, and Revision note says `NY REVISJON`. Otherwise Revision note is empty. `[ASSUMPTION]` on the Revision note column.
- After the file is generated, the new-revision mark of every job in the file is cleared.
- Generating a file for another supplier does not clear the mark.

### 4.3 Import and Validation

**Description:** The production planner uploads a returned supplier file. PTS first runs the file checks. If one fails, the file is rejected with a message, and no import is created. Otherwise PTS checks every row, creates a pending import and shows its change view. Nothing is written to job data at this stage. Rule IDs are those of the brief. Realizes UJ-2, UJ-5, UJ-6.

**Functional Requirements:**

#### FR-11: Upload a supplier file

**Priority: Core.** The production planner can upload a supplier file. Realizes UJ-2.

**Consequences (testable):**
- PTS reads the Export ID from the file and finds the export and supplier from it. The planner does not select them.
- Uploading creates a pending import or shows a file-check rejection message, within the limits in §5.

#### FR-12: File checks (F1–F4)

**Priority: Core.** The whole file is rejected, and no import is created, when:

- **F1** — the file is not an `.xlsx` file, or cannot be read.
- **F2** — one or more template columns are missing or renamed.
- **F3** — the Export ID is missing, was not generated by PTS, or differs between rows.
- **F4** — the file contains no job rows.

**Consequences (testable):**
- The message names the rule and the problem, for example: «F2: Kolonnen *Antall ferdig* mangler».
- File-check rejections are shown but not stored in the import log (§7.2).

#### FR-13: Row rejection rules (R1–R7)

**Priority: Core.** A row is rejected, and never applied, when:

- **R1** — production status is not an allowed value, including a Norwegian value with no mapping (NFR-10).
- **R2** — status is `On hold` without an on hold reason, or the reason is `Other` without a comment.
- **R3** — status is `Ready for inspection` without an inspection type.
- **R4** — completed quantity is not a whole number, is negative, or is greater than the job's quantity in PTS.
- **R5** — expected completion date is not a valid date.
- **R6** — the Job ID does not exist in PTS, or the job belongs to a different supplier than the export.
- **R7** — the same Job ID appears more than once in the file. All rows with that Job ID are rejected.

**Consequences (testable):**
- Each rejected row shows the Job ID, the rule ID and a message, for example: «R2: Status er Stoppet, men årsak til stopp mangler».
- A row breaking several rules lists all of them.
- An empty expected completion date is allowed and means "not given". `[ASSUMPTION]`
- For R5, PTS accepts real Excel dates and dates written as text in `dd.mm.yyyy` or `yyyy-mm-dd`. Any other text is rejected. `[ASSUMPTION]` on the two formats.
- Status `Completed` with a completed quantity below the quantity is allowed. `[ASSUMPTION]`

#### FR-14: Warning rules (W8–W15)

**Priority: per warning, as marked.** A row, or the whole import for W9, gets a warning when one of the conditions below holds. Warnings do not stop approval.

- **W8 Revision mismatch** (Core) — the revision in the file differs from the job's current revision.
- **W9 Outdated file** (Extension) — a newer export exists for the same supplier. Applies to the whole import and is checked whenever the import is shown.
- **W10 Unexpected change** (Core) — a value in a locked column differs from its exported value. Locked-column values are never applied.
- **W11 Delay** (Core) — expected completion date is later than the due date.
- **W12 Status moved backwards** (Extension) — the file's production status comes earlier than the job's current status in the order *Not started → In production / On hold → Ready for inspection → Completed*.
- **W13 Missing job** (Extension) — an open job that was in the export is missing from the file. The job is left unchanged.
- **W14 Job changed by another import** (Extension) — after the export, another approved import changed a supplier-reported field of this job, and this file changes the same field to a different value.
- **W15 Conflict with manual update** (Extension, built with FR-28) — after the export, a manual update changed a supplier-reported field of this job, and the file's value for that field differs from the job's current value. This applies whether the supplier changed the cell or not.

**Consequences (testable):**
- Each warning shows its rule ID and a Norwegian message naming the values involved, for example: «W15: PTS har *I produksjon* (manuell oppdatering 10.11.2026, Ingrid), fila har *Stoppet*».
- W14 and W15 are shown per field, so the planner sees which field is in conflict.

#### FR-15: Change view

**Priority: Core.** For each pending import, the production planner sees what would change on approval. Realizes UJ-2, UJ-5.

**Consequences (testable):**
- **Per job:** each supplier-changed cell, with the value in PTS now and the value in the file. Only these are applied on approval.
- A cell that is not supplier-changed but differs from the job's current value is shown as *kept* (the PTS value stays) with W14 or W15, and is not applied.
- Jobs with no supplier-changed cells are listed as *No change* (*Ingen endring*).
- Rejected rows and warnings are listed with rule IDs and can be filtered.
- A summary at the top shows the number of changed jobs, unchanged jobs, rejected rows and warnings.
- Opening the change view never changes job data.

**Notes:** A low-fidelity sketch is in `addendum.md` §A3.3, and the screen list in §A3.1. UX refines the layout.

#### FR-16: Revision reported per import

**Priority: Core.** For each import, PTS stores the revision each row reported.

**Consequences (testable):**
- The import log shows the reported revision per row, even after the job's current revision has changed.

#### FR-30: Conditional fields follow the status

**Priority: Core.** On hold reason and inspection type are stored only together with the status they belong to.

**Consequences (testable):**
- When an approved import or a manual update sets a status other than `On hold`, the job's on hold reason is cleared.
- When the status is set to something other than `Ready for inspection`, the inspection type is cleared.
- A file row with a reason or inspection type that does not fit its status is not rejected. The value is ignored, and the change view says so. `[ASSUMPTION]`
- The comment is kept regardless of status.

### 4.4 Approval and Import Log

**Description:** The production planner approves or rejects a pending import as a whole. Approval applies all supplier-changed cells of non-rejected rows in one operation. Several pending imports may exist at once. Every decision is logged. Realizes UJ-2, UJ-5, UJ-6.

**Functional Requirements:**

#### FR-17: No change before approval

**Priority: Core.** Job data is never changed by uploading, validating or viewing an import.

**Consequences (testable):**
- Automated tests show that job data is identical before and after upload, validation and viewing a change view, for every example file.

#### FR-18: Approve or reject a whole import

**Priority: Core.** The production planner can approve or reject a pending import. Realizes UJ-2.

**Consequences (testable):**
- **Approve:** all supplier-changed cells of non-rejected rows are applied in one all-or-nothing operation. If anything fails, nothing is applied.
- **Reject:** nothing is applied.
- Rejected rows are never applied, even when the import is approved.
- Cells that are not supplier-changed are never applied (FR-8).
- Every applied change is recorded in the job history (FR-5), linked to the import log entry. FR-18 owns writing job history for imports, FR-28 for manual updates, and FR-29 for closes and reopens.
- An approved or rejected import cannot be decided again.
- Individual rows cannot be approved or rejected (§7.2).

#### FR-19: Several pending imports

**Priority: Core.** Several pending imports may exist at once, also for the same supplier and the same jobs. Realizes UJ-6.

**Consequences (testable):**
- Uploading a second file for a supplier with a pending import succeeds and creates a second pending import.
- The list of pending imports shows supplier, Export ID, file name and upload time.

#### FR-20: Always current

**Priority: Core.** The validation result and change view of a pending import always reflect the current job data. Realizes UJ-6.

**Consequences (testable):**
- After another import is approved, the change view of every other pending import shows the updated values in the PTS column.
- After a quantity edit (FR-2), a row whose completed quantity now exceeds the quantity fails R4.
- W14 appears on another pending import after an approval only when that import changes the same field to a different value (Extension).

#### FR-21: Import log

**Priority: Core.** Every approved or rejected import is logged.

**Consequences (testable):**
- Each entry has date and time, file name, Export ID, supplier, user name, result (*Godkjent* / *Avvist*), and counts of changed jobs, rejected rows and warnings.
- From an entry, the planner can see the change view as it was when the import was decided, including the revision each row reported (FR-16).
- Log entries cannot be edited or deleted in the app.

#### FR-22: Fixed user name

**Priority: Core.** With no login in v1, PTS records a configured user name on every approval, rejection, manual update, close and reopen.

**Consequences (testable):**
- The user name is set in configuration, with a default for the demo, for example "Planlegger (demo)".
- The import log and the job history show it.

### 4.5 Dashboard

**Description:** The dashboard is the production planner's starting point. It lists jobs with their key fields and flags, and lets the planner find everything that needs action in a few clicks. Realizes UJ-4.

**Functional Requirements:**

#### FR-23: Job overview

**Priority: Core.** The dashboard lists jobs with these fields:

- Job ID
- drawing number and current revision
- description
- quantity and completed quantity
- supplier
- production status and on hold reason
- inspection type
- due date and expected completion date
- comment / issue description
- last export date
- flags (FR-24)

**Consequences (testable):**
- A newly created job appears with all these fields.
- Jobs can be sorted by due date and filtered by supplier.

#### FR-24: Flags

**Priority: Core.** Each job shows the flags that apply:

- **On hold** — with the reason.
- **Ready for inspection** — with the inspection type.
- **Delayed** — expected completion date later than due date.
- **New revision — send updated file to supplier** — the job has a new-revision mark.
- **Revision mismatch** — an approved import reported a revision other than the job's current revision at the time of approval. Rejected rows do not count. The flag is cleared when a later approved import reports the current revision, or when the planner registers a new revision (the new-revision mark then takes over).
- **Has comment** — the comment / issue description is not empty.

**Consequences (testable):**
- A job with expected completion date 09.12.2026 and due date 27.11.2026 shows *Delayed*.
- The *New revision* flag disappears when a supplier file containing the job is generated.
- Registering a new revision does not raise *Revision mismatch* on its own.

#### FR-25: Action filters

**Priority: Core.** The production planner can filter the dashboard to jobs that are on hold, ready for inspection, delayed, or affected by a new revision (new revision or revision mismatch). Realizes UJ-4.

**Consequences (testable):**
- Each filter shows exactly the jobs with that flag and no others.
- The number of jobs per filter is visible without applying it.
- By default, only open jobs are shown, with an option to include closed jobs. `[ASSUMPTION]`

### 4.6 Demo Data and Example Files

**Description:** Anyone, including the examiner, can run PTS locally and try the full flow with fictional data, without a real supplier.

**Functional Requirements:**

#### FR-26: Seed data and reset

**Priority: Core.** PTS can be loaded with fictional seed data, and reset to it with one command.

**Consequences (testable):**
- The seed data has at least three suppliers and enough jobs to show every production status and every flag.
- The seed data includes the exports that the example files (FR-27) were generated from, with their stored values. It also includes one supplier with two exports, and one job whose revision changed after export.
- The reset command restores the seed state, so the example files give their expected results again after a trial run.

#### FR-27: Example supplier files

**Priority: Core.** The repository includes example supplier files in `testdata/` with documented expected results. They are used by automated tests and for manual trial.

| File | Content | Expected result |
|---|---|---|
| `valid.xlsx` | Correct updates for several jobs | All rows accepted, changes shown |
| `not-xlsx.csv` | A CSV file | File rejected (F1) |

## 5. Cross-Cutting Non-Functional Requirements

- **NFR-1 Data integrity.** Job data changes only through:
  - the job register: FR-1, FR-2, FR-3, FR-28 and FR-29
  - generating a supplier file, which clears new-revision marks (FR-10)
  - an approved import (FR-18), which is all-or-nothing
- **NFR-2 Traceability.** Every change to supplier-reported fields, and every close and reopen, can be traced through the job history to one import log entry or one manual update.
- **NFR-3 Runnable locally.** PTS runs on a single developer machine by following the README. It needs no paid services, no external accounts and none of the team's own keys. The README covers:
  - install
  - starting the app
  - seeding and resetting (FR-26)
  - running the tests
  - trying UJ-1 and UJ-2 with the example files
- **NFR-4 Safe file handling.**
  - Only `.xlsx` files are accepted. Macro-enabled files (`.xlsm`) are rejected by F1.
  - Uploads are limited to 5 MB. `[ASSUMPTION]`
  - File content is only read as data and is never executed.
  - Uploaded files are kept as long as their import and log entry need them. `[ASSUMPTION]`
- **NFR-5 Responsiveness.** Validating a supplier file of up to 200 rows and showing its change view takes under 5 seconds on a typical laptop. `[ASSUMPTION]`
- **NFR-6 Understandable messages.** Every rejection and warning names its rule ID and says in plain Norwegian what is wrong and, where possible, what the values were.
- **NFR-7 Testability.** Automated tests cover every validation rule (F1–F4, R1–R7, W8–W15), FR-17 and the approval rules in FR-18.
- **NFR-8 Fictional data only.** No real company data, drawings or supplier names in the repository, seed data or example files. The real-world case involves classified documentation.
- **NFR-9 Platform.** A desktop web application, used in a current version of Chrome or Edge. Mobile is not supported in v1. `[ASSUMPTION]`
- **NFR-10 Language.** Everything a user or supplier sees is in Norwegian, using the labels in §3.1. This covers the user interface, messages, the supplier file and the rule messages.
  - Stored values (status, reason, inspection type) use the English Glossary terms internally and are shown with their Norwegian labels.
  - On import, the Norwegian values in the file are mapped to the stored values. A value with no mapping fails R1.
  - Dates are shown as `dd.mm.yyyy` everywhere.
  - Rule IDs (F1, R2, W15 …) are the same in every language.
  - The example messages in this PRD show content, not final wording.
  - The PRD, code and documentation are in English (project rule).
- **NFR-11 Repository hygiene.** The local database, uploaded files and generated supplier files are excluded from git. The app needs no secrets. Configuration, such as the user name in FR-22, has a committed example file with safe defaults. Example files and seed data live in `testdata/`.

## 6. Non-Goals (Explicit)

- PTS does not replace ERP, PDM, PLM, MES or quality systems, and is not a system of record for engineering or finance.
- PTS does not store engineering drawings as the authoritative source.
- PTS does not send email or integrate with shared folders. File transfer is manual.
- PTS does not give suppliers access to internal systems.
- PTS does not approve technical or quality decisions automatically.
- PTS does not become a warehouse, logistics or financial system.
- PTS does not plan production. It tracks status.

## 7. MVP Scope

### 7.1 In Scope (v1), by Priority

**Core** — the flow that must be finished and stable first: create job → generate supplier file → import → change view → approve → dashboard.

- Job register: create, edit, new revision, job detail (FR-1, FR-2, FR-3, FR-5)
- Supplier file: generate, fixed Norwegian template, pre-filled values, dropdowns, new-revision marking (FR-6 … FR-10)
- Import: upload, file checks, row rules, warnings W8, W10 and W11, change view, reported revision, conditional fields (FR-11 … FR-16, FR-30)
- Approval: no change before approval, approve/reject, several pending imports, always current, import log, user name (FR-17 … FR-22)
- Dashboard: overview, flags, filters (FR-23 … FR-25)
- Seed data, reset and example files (FR-26, FR-27)

**Extension** — built after Core is stable, in this order `[ASSUMPTION]` on the order:

1. Manual update and W15 (FR-28)
2. Close and reopen jobs (FR-29)
3. Warnings W9, W12, W13 and W14 (FR-14)
4. Supplier management (FR-4)

### 7.2 Out of Scope for v1

- Recording inspection results, delivery, internal assembly and final approval. Deferred to later versions to protect the core flow this semester.
- Several internal users, roles and login (Windows / Microsoft Entra ID). Later versions.
- Revision history. PTS stores only the current revision.
- Approving or rejecting individual rows in an import. Later versions.
- Automatic notification of the project manager and job owner on revision changes. Later versions.
- History of edits made through FR-2 and FR-3. Only supplier-reported fields, closes and reopens are recorded in the job history.
- Logging of file-check rejections. They are shown but not stored.
- Deleting jobs or suppliers. Jobs are closed instead (FR-29).

## 8. Success Metrics

The v1 success criteria are functional and checked by tests and a demo run. SM-N corresponds to success criterion N in the brief.

**Primary**
- **SM-1** — A created job appears on the dashboard with all fields in FR-23. Validates FR-1, FR-23.
- **SM-2** — A supplier file contains only that supplier's open jobs, a unique Export ID and each job's current revision. Validates FR-6, FR-7.
- **SM-3** — Every rejected row is shown with an understandable message naming the broken rule. Validates FR-13, NFR-6.
- **SM-4** — Before approval, the change view shows exactly which cells change per job. Validates FR-15.
- **SM-5** — No import changes job data before it is approved, verified by tests. Validates FR-17.
- **SM-6** — A file reporting an older revision is flagged as a revision mismatch. Validates FR-14 (W8).
- **SM-7** — A job whose expected completion date is later than its due date is flagged as delayed. Validates FR-24.
- **SM-8** — When two pending imports share a job and one is approved, the other shows the updated values, and W14 where it would overwrite them. Validates FR-19, FR-20, FR-14 (W14).
- **SM-9** — From the dashboard alone, the planner finds all jobs on hold, ready for inspection, delayed, or affected by a new revision. Validates FR-25.
- **SM-10** — Status, on hold reason and inspection type are dropdowns with only the allowed values. Validates FR-9.
- **SM-11** — A new revision is marked on the dashboard and in the next supplier file, and the dashboard mark disappears after export. Validates FR-3, FR-10, FR-24.
- **SM-12** — A file that is not a valid PTS supplier file is rejected as a whole with a clear message. Validates FR-12.

**Secondary**
- **SM-13** — Every example file produces its expected result per row in the automated tests. Validates FR-27, NFR-7.
- **SM-14** — The examiner can run PTS and complete UJ-1 and UJ-2 from the README alone. Validates NFR-3, FR-26.
- **SM-15** — A file that disagrees with a manual update made after the export shows W15. Approving it never applies untouched cells. Validates FR-28, FR-14 (W15), FR-8.
- **SM-16** — Every change to supplier-reported fields appears in the job history, linked to an import log entry or a manual update. Validates FR-5, FR-21, NFR-2.

**Counter-metrics (guards, checked in UX review and tests)**
- **SM-C1** — Warnings are never hidden or collapsed by default in the change view, and no setting turns a warning off. Counterbalances SM-3 and SM-4.
- **SM-C2** — **Approve import** is never the default or pre-focused action, and approval always needs a deliberate click on the change view. Counterbalances SM-4 and SM-5.
