## 1. Vision

PTS is an internal web application that gives a production planner one reliable overview of production jobs placed with external suppliers. It answers one question quickly: *"Where is this job, and is there anything we need to act on?"*

Suppliers never get access to the company's systems. Instead, PTS generates a controlled Excel file per supplier with the same fields the planner sees in the app. The supplier fills in production status, completed quantity, expected completion date and any issues, and returns the file. PTS checks every row, shows exactly what would change, and updates the database only when the planner approves.

The value is trust in the data. Today, status lives in scattered Excel files and emails, and it is hard to know which version is current. PTS makes the database the single current picture, makes every change traceable to an approved import, and makes problems visible early: jobs on hold, inspection requests, delays and suppliers working from an outdated drawing revision.

## 2. Target User

### 2.1 Jobs To Be Done

- **Functional:** know the current status of every job at every supplier without phoning or emailing around.
- **Functional:** send a supplier a clear, up-to-date list of their jobs and get structured updates back.
- **Functional:** catch problems early — a job on hold, a request for inspection, a delay, or a supplier still working from an old drawing revision.
- **Contextual:** work within a controlled IT environment where suppliers cannot access internal systems, and file transfer happens by email or a shared folder.
- **Emotional:** be confident that nothing in the database changed without the planner seeing and approving it.

### 2.2 Users in v1

- **Production planner** — the one internal role in v1. Creates jobs, generates supplier files, imports returned files, approves or rejects imports, registers new drawing revisions and follows up from the dashboard.
- **Supplier** — indirect user. Never uses PTS; only receives and returns the supplier file.

### 2.3 Non-Users (v1)

- Project, engineering, quality and inspection personnel as separate roles (later versions).
- Suppliers as direct users of PTS.

### 2.4 Key User Journeys

The persona is fictional: **Ingrid, production planner** at a marine engineering company, responsible for about 40 open jobs across five machining and welding suppliers.

**UJ-1. Ingrid registers new jobs and sends Supplier Alpha their file.**
- **Entry state:** PTS is open in the browser on her desktop. No login in v1.
- **Path:**
  1. She creates three new jobs for Supplier Alpha, entering drawing number, revision, description, quantity, supplier and due date for each.
  2. She opens Supplier Alpha and clicks **Generate supplier file**.
  3. PTS downloads an `.xlsx` file with all of Supplier Alpha's open jobs, a unique Export ID and the current values pre-filled.
  4. She attaches the file to an email to the supplier, outside PTS.
- **Climax:** the file opens in Excel with locked grey columns, yellow editable columns and dropdown lists. She knows the supplier cannot pick an invalid status.
- **Resolution:** the export is recorded for Supplier Alpha. Jobs with a new-revision mark lose the mark because the supplier now has the updated file.
- Realized by FR-1, FR-2, FR-6 … FR-10.

**UJ-2. Ingrid imports Supplier Alpha's returned file and approves it.**
- **Entry state:** Supplier Alpha has emailed the file back. Ingrid saves it locally.
- **Path:**
  1. She opens **Import supplier file** and uploads the file.
  2. PTS checks the file as a whole, then every row, and creates a pending import.
  3. The change view shows, per job, old and new values, which rows are rejected and why, and which rows carry warnings.
  4. She sees that PTS-0003 is now *On hold — Missing material* and that PTS-0002 reports revision B while the current revision is C.
  5. She clicks **Approve import**.
- **Climax:** the dashboard immediately shows PTS-0003 as on hold and PTS-0002 with a revision mismatch warning. She knows exactly what changed because she approved it line by line on one screen.
- **Resolution:** the import is in the import log with date, file name, user and result. She phones the supplier about the outdated drawing.
- **Edge cases:**
  - The file is not a PTS supplier file (wrong columns, no Export ID). PTS rejects the whole file with a clear message, and no pending import is created.
  - A row has status *On hold* without a reason. That row is rejected and shown with rule R2, and the other rows can still be approved.
- Realized by FR-11 … FR-22.

**UJ-3. Ingrid registers a new drawing revision.**
- **Entry state:** engineering has approved revision C of drawing DRW-10002. Ingrid has placed the drawing in the shared folder and emailed the project manager and job owner, as today.
- **Path:**
  1. She opens job PTS-0002 and changes the current revision from B to C.
  2. The job gets a *New revision* badge on the dashboard.
  3. Next time she generates Supplier Alpha's file, the Revision cell of PTS-0002 is highlighted and says `NEW REVISION`.
- **Climax:** the supplier cannot miss that the drawing has changed, and Ingrid cannot forget to tell them.
- **Resolution:** the badge disappears once the new file has been downloaded. Any later import that still reports revision B is flagged as a revision mismatch.
- Realized by FR-3, FR-8, FR-9, FR-15 (W8).

**UJ-4. Ingrid follows up in the morning.**
- **Entry state:** start of the working day.
- **Path:**
  1. She opens the dashboard.
  2. She filters on *On hold*, then on *Ready for inspection*, then on *Delayed*, then on *New revision or revision mismatch*.
- **Climax:** she has a short list of jobs to act on without opening any Excel file.
- **Resolution:** she books an inspection before painting for PTS-0004 and follows up the delayed jobs.
- **Edge case:** the supplier phones and says the missing material for PTS-0003 has arrived. Ingrid sets the job back to *In production* as a manual update. The change is recorded in the job history with her name, and a pending import containing PTS-0003 gets W14.
- Realized by FR-23 … FR-25, FR-28.

**UJ-5. Two returned files for the same supplier wait at the same time.**
- **Entry state:** Supplier Alpha returned a file on Monday, which is still pending, and a corrected file on Tuesday.
- **Path:**
  1. Ingrid uploads Tuesday's file. PTS accepts it as a second pending import.
  2. She approves Tuesday's import first.
  3. Monday's pending import is recalculated against the updated database. Rows for the same jobs now show warning W14 *Job changed since upload*, and Monday's file also carries W9 *Outdated file*.
- **Climax:** she sees that Monday's file would undo Tuesday's update and rejects it.
- **Resolution:** both decisions are in the import log.
- Realized by FR-19, FR-20.

## 3. Glossary

- **Job** — one production order placed with one supplier for one drawing. Has a Job ID, drawing number, current revision, description, quantity, supplier, due date and supplier-reported fields. Belongs to exactly one supplier.
- **Job ID** — unique identifier of a job, generated by PTS (e.g. `PTS-0001`). `[ASSUMPTION]`
- **Supplier** — an external workshop that produces jobs. Has a name. Has zero or more jobs.
- **Drawing number** — identifier of the engineering drawing the job is produced from. The drawing itself lives outside PTS.
- **Current revision** — the drawing revision the job must be produced to, as registered in PTS. PTS stores only the current revision, not a history.
- **New-revision mark** — a flag on a job set when the production planner changes its current revision, and cleared when a supplier file containing the job has been generated.
- **Open job** — a job whose production status is not `Completed`. Jobs are not closed manually in v1.
- **Production status** — one of `Not started`, `In production`, `On hold`, `Ready for inspection`, `Completed`.
- **On hold reason** — one of `Drawing issue`, `Missing material`, `Check requested`, `Other`. Required when the production status is `On hold`.
- **Inspection request** — a supplier's request for inspection, given by production status `Ready for inspection` plus an inspection type: `Before painting` or `Final`.
- **Supplier-reported fields** — production status, on hold reason, inspection type, completed quantity, expected completion date and comment. The only fields an import may change.
- **Supplier file** — the `.xlsx` file PTS generates for one supplier, following the fixed template, with locked columns and editable columns.
- **Export** — the record that a supplier file was generated: Export ID, export date, supplier, and the jobs and values it contained.
- **Export ID** — unique identifier of one export, printed in every row of the supplier file.
- **Import** — one uploaded supplier file, together with its validation result and change view. Has a state: `Pending`, `Approved`, `Rejected`.
- **Pending import** — an import waiting for the production planner to approve or reject it. Several can exist at once, also for the same supplier.
- **File check** — a check on the uploaded file as a whole (rules F1–F4). A failed file check rejects the file, and no import is created.
- **Rejected row** — a row in an import that broke a rejection rule (R1–R7). Never applied to the database.
- **Warning** — a flag on a row or file that does not stop the import (W8–W14). Applied on approval, but shown to the production planner.
- **Change view** — the screen showing, for one import, what would change per job compared to the database, plus rejected rows and warnings.
- **Approve / Reject** — the production planner's decision on a whole import.
- **Import log** — the permanent record of every approved or rejected import.
- **Manual update** — a change the production planner makes by hand to a job's supplier-reported fields, for example after a phone call with the supplier. Recorded in the job history.
- **Job history** — the permanent record, per job, of every change to its supplier-reported fields, each linked to either an import log entry or a manual update.
- **Dashboard** — the main overview of jobs, with flags and filters.
- **Delayed** — a job whose expected completion date is later than its due date.
- **Revision mismatch** — warning W8: the revision in the supplier file differs from the job's current revision.

## 4. Features

### 4.1 Job Register

**Description:** The production planner creates, views and edits jobs, and manages the list of suppliers. The job fields in the app are the same as the columns in the supplier file, so what the planner sees and what the supplier sees match. Whether the register is a spreadsheet-like table or a table with a separate form is left to UX. Supplier-reported fields change through an approved import, or through a manual update when the planner learns something outside the file, for example by phone. Both are recorded in the job history, so every change can be traced. Realizes UJ-1, UJ-3, UJ-4.

**Functional Requirements:**

#### FR-1: Create a job

The production planner can create a job with drawing number, revision, description, quantity, supplier and due date. Realizes UJ-1.

**Consequences (testable):**
- All six fields are required. Saving without one shows which field is missing.
- Quantity must be a whole number of 1 or more.
- Due date must be a valid date.
- PTS assigns a unique Job ID.
- A new job has production status `Not started`, completed quantity 0, and appears on the dashboard immediately.

#### FR-2: View and edit a job

The production planner can view all fields of a job and edit drawing number, description, quantity, supplier and due date. Realizes UJ-1.

**Consequences (testable):**
- The job view shows every field listed in FR-23.
- Supplier-reported fields are changed through FR-28, not through this form.
- Quantity cannot be set below the job's current completed quantity.

#### FR-3: Register a new revision

The production planner can change the current revision of a job. Realizes UJ-3.

**Consequences (testable):**
- After saving a different revision, the job has a new-revision mark.
- The previous revision is not stored on the job. Earlier imports in the import log keep the revision they reported.
- Saving the same revision again does not set a new-revision mark.

#### FR-4: Manage suppliers

The production planner can create a supplier with a name and see the list of suppliers. `[ASSUMPTION]`

**Consequences (testable):**
- Supplier names are unique.
- A supplier with jobs cannot be deleted.

**Notes:** Seed data provides fictional suppliers (FR-26), so supplier management can stay minimal.

#### FR-5: Job states visible in the register

The job register shows, per job, the flags defined in FR-24, so the planner can see them from the job view as well as from the dashboard.

#### FR-28: Manual update of supplier-reported fields

The production planner can change a job's supplier-reported fields by hand, as a manual update. Realizes UJ-4.

**Consequences (testable):**
- The same rules as for imported rows apply (R1–R5). A manual update breaking a rule cannot be saved, and the rule ID and message are shown.
- Every manual update is recorded in the job history with date and time, user name (FR-22), field, old value and new value.
- A manual update counts like an approved import for pending imports: pending imports containing the job are recalculated, and the affected rows get W14 (FR-20).
- The job history of a job lists manual updates and approved imports in time order.

### 4.2 Supplier File Generation

**Description:** When the production planner has entered what is needed, they click **Generate supplier file** for one supplier. There is no separate "ready" or "finalize" step. PTS creates a `.xlsx` file from the fixed template with all of that supplier's open jobs, records the export, and downloads the file. The planner sends it outside PTS by email or a shared folder. The draft template is `pts-supplier-template.xlsx` in this folder. Realizes UJ-1, UJ-3.

**Functional Requirements:**

#### FR-6: Generate a supplier file

The production planner can generate a supplier file for one supplier. Realizes UJ-1.

**Consequences (testable):**
- The file contains one row per open job of that supplier, and no jobs of other suppliers.
- Every row carries the same, unique Export ID and the export date.
- Generating a file for a supplier with no open jobs shows a message, and no file or export is created.

#### FR-7: Fixed template

The supplier file follows the fixed template.

**Consequences (testable):**
- **Locked columns, in this order:** Export ID, Export date, Job ID, Drawing number, Revision, Revision note, Description, Quantity, Supplier, Due date.
- **Editable columns, in this order:** Production status, On hold reason, Inspection type, Completed quantity, Expected completion date, Comment / issue description.
- Locked columns are protected and visually distinct (grey), and editable columns are unlocked (yellow). Sheet protection has no password. `[ASSUMPTION]`
- The file contains an instructions sheet explaining how to fill it in and the rules from §4.3, in English. `[ASSUMPTION]`
- Internal-only information, such as inspection results, is not included.

#### FR-8: Pre-filled current values

The editable columns are pre-filled with the job's current supplier-reported values from PTS.

**Consequences (testable):**
- For a job with status `In production` and completed quantity 4, the exported row shows `In production` and 4.
- On import, an editable cell whose value equals the exported value produces no change for that field.

#### FR-9: Dropdowns and cell validation

The editable columns guide the supplier towards valid values.

**Consequences (testable):**
- Production status, On hold reason and Inspection type are dropdown lists containing exactly the allowed values.
- Completed quantity accepts only whole numbers from 0 to the row's quantity.
- Expected completion date accepts only dates.
- Missing conditional fields are highlighted, for example *On hold* without a reason.
- PTS does not rely on these: every rule is checked again on import (§4.3).

#### FR-10: New revision in the file and clearing the mark

Jobs with a new-revision mark are marked in the supplier file, and the mark is cleared by the export. Realizes UJ-3.

**Consequences (testable):**
- A job whose current revision changed since the previous export to its supplier has its Revision cell highlighted, and Revision note says `NEW REVISION`. Otherwise Revision note is empty.
- After the file is generated, the new-revision mark of every job in the file is cleared.
- Generating a file for another supplier does not clear the mark.

### 4.3 Import and Validation

**Description:** The production planner uploads a returned supplier file. PTS first runs the file checks. If one fails, the file is rejected with a message and no import is created. Otherwise PTS checks every row, creates a pending import and shows its change view. Nothing is written to the job data at this stage. Rule IDs are those of the brief. Realizes UJ-2, UJ-5.

**Functional Requirements:**

#### FR-11: Upload a supplier file

The production planner can upload a supplier file. Realizes UJ-2.

**Consequences (testable):**
- PTS reads the Export ID and supplier from the file. The planner does not have to select them.
- Uploading creates a pending import, or a file-check rejection message, within the limits in §5.

#### FR-12: File checks (F1–F4)

The whole file is rejected, and no import is created, when:

- **F1** — the file is not an `.xlsx` file, or cannot be read.
- **F2** — one or more template columns are missing or renamed.
- **F3** — the Export ID is missing or was not generated by PTS.
- **F4** — the file contains no job rows.

**Consequences (testable):**
- The message names the rule (e.g. "F2: column *Completed quantity* is missing").
- Each of F1–F4 is covered by an example file and an automated test.

#### FR-13: Row rejection rules (R1–R7)

A row is rejected, and never applied, when:

- **R1** — production status is not an allowed value.
- **R2** — status is `On hold` without an on hold reason, or the reason is `Other` without a comment.
- **R3** — status is `Ready for inspection` without an inspection type.
- **R4** — completed quantity is not a whole number, is negative, or is greater than the ordered quantity in PTS.
- **R5** — expected completion date is not a valid date.
- **R6** — the Job ID does not exist in PTS, or belongs to a different supplier than the export.
- **R7** — the same Job ID appears more than once in the file. All rows with that Job ID are rejected.

**Consequences (testable):**
- Each rejected row shows the Job ID, the rule ID and an understandable message (e.g. "R2: Status is On hold, but no reason is given").
- A row breaking several rules lists all of them.
- An empty expected completion date is allowed and means "not given". `[ASSUMPTION]`
- For R5, PTS accepts real Excel dates and dates written as text in the formats `dd.mm.yyyy` and `yyyy-mm-dd`. Any other text is rejected. `[ASSUMPTION]` on the two formats.

#### FR-14: Warning rules (W8–W14)

A row (or the whole file, for W9) gets a warning, but is still applied on approval, when:

- **W8 Revision mismatch** — the revision in the file differs from the job's current revision.
- **W9 Outdated file** — a newer export exists for the same supplier. Applies to the whole import.
- **W10 Unexpected change** — a value in a locked column differs from the value in the export.
- **W11 Delay** — expected completion date is later than the due date.
- **W12 Status moved backwards** — the new production status is earlier in the order *Not started → In production / On hold → Ready for inspection → Completed*.
- **W13 Missing job** — an open job that was in the export is missing from the file. The job is left unchanged.
- **W14 Job changed since upload** — after this file was uploaded, the job was changed by another approved import or a manual update (FR-20, FR-28).

**Consequences (testable):**
- Each warning shows its rule ID and a message naming the old and new value where relevant.
- Changes in locked columns (W10) are never applied to the database. Only supplier-reported fields are. `[ASSUMPTION]`

#### FR-15: Change view

For each pending import, the production planner sees what would change. Realizes UJ-2.

**Consequences (testable):**
- **Per job:** each supplier-reported field that would change, with the old value (database) and the new value (file).
- Jobs with no changes are listed as *No change*.
- Rejected rows and warnings are listed with rule IDs and can be filtered.
- A summary at the top shows the number of changed jobs, unchanged jobs, rejected rows and warnings.
- Opening the change view never changes job data.

**Notes:** A low-fidelity sketch of the change view is in `addendum.md` §A3. Layout is for UX to refine.

#### FR-16: Revision reported per import

PTS stores, for each import, the revision each row reported, so the import log can show it even though jobs store only the current revision.

### 4.4 Approval and Import Log

**Description:** The production planner approves or rejects a pending import as a whole. Approval applies all non-rejected rows in one operation. Several pending imports may exist at once. When one is approved, the others are recalculated against the updated database, so the planner always approves against current data and the last approved import wins. Every decision is logged. Realizes UJ-2, UJ-5.

**Functional Requirements:**

#### FR-17: No change before approval

Job data is never changed by uploading, validating or viewing an import.

**Consequences (testable):**
- Automated tests show that job data is identical before and after upload, validation and viewing a change view, for every example file.

#### FR-18: Approve or reject a whole import

The production planner can approve or reject a pending import. Realizes UJ-2.

**Consequences (testable):**
- **Approve:** all supplier-reported changes from non-rejected rows are applied in one all-or-nothing operation. If anything fails, nothing is applied.
- **Reject:** nothing is applied.
- Rejected rows are never applied, even when the import is approved.
- An approved or rejected import cannot be approved or rejected again.
- Individual rows cannot be approved or rejected (§6).

#### FR-19: Several pending imports

Several pending imports may exist at once, also for the same supplier and the same jobs. Realizes UJ-5.

**Consequences (testable):**
- Uploading a second file for a supplier with a pending import succeeds and creates a second pending import.
- The list of pending imports shows supplier, Export ID, file name and upload time.

#### FR-20: Recalculate after approval

When an import is approved, or a manual update is saved (FR-28), every pending import containing one or more of the same jobs is recalculated against the updated database. Realizes UJ-5.

**Consequences (testable):**
- The change view of those imports shows old values from the updated database.
- The affected rows get W14.
- If the approved import came from a newer export, the other imports also get W9.

#### FR-21: Import log

Every approved or rejected import is logged.

**Consequences (testable):**
- Each entry has date and time, file name, Export ID, supplier, user name, result (Approved / Rejected), and counts of changed jobs, rejected rows and warnings.
- From an entry, the planner can see the change view as it was when decided, including the revision each row reported (FR-16).
- Log entries cannot be edited or deleted in the app.

#### FR-22: Fixed user name

With no login in v1, PTS records a configured user name on every approval or rejection.

**Consequences (testable):**
- The user name is set in configuration, and the import log shows it.

### 4.5 Dashboard

**Description:** The dashboard is the production planner's starting point. It lists all jobs with their key fields and flags, and lets the planner find everything that needs action in a few clicks. Realizes UJ-4.

**Functional Requirements:**

#### FR-23: Job overview

The dashboard lists jobs with: Job ID, drawing number and current revision, description, quantity, supplier, production status and on hold reason, inspection type, completed quantity, due date, expected completion date, and flags (FR-24).

**Consequences (testable):**
- A newly created job appears with all these fields.
- Jobs can be sorted by due date and filtered by supplier.

#### FR-24: Flags

Each job shows the flags that apply:

- **On hold** — with the reason.
- **Ready for inspection** — with the inspection type.
- **Delayed** — expected completion date later than due date.
- **New revision** — has a new-revision mark.
- **Revision mismatch** — the last approved import for the job reported a revision other than the current one. `[ASSUMPTION]`

**Consequences (testable):**
- A job with expected completion date 2026-12-09 and due date 2026-11-27 shows *Delayed*.
- The *New revision* flag disappears when a supplier file containing the job is generated.
- The *Revision mismatch* flag disappears when a later approved import reports the current revision.

#### FR-25: Action filters

The production planner can filter the dashboard to jobs that are on hold, ready for inspection, delayed, or affected by a new revision (new revision or revision mismatch). Realizes UJ-4.

**Consequences (testable):**
- Each filter shows exactly the jobs with that flag and no others.
- The number of jobs per filter is visible without applying it.
- By default, only open jobs are shown, with an option to include completed jobs. `[ASSUMPTION]`

### 4.6 Demo Data and Example Files

**Description:** Anyone, including the examiner, can run PTS locally and try the full flow with fictional data, without a real supplier.

**Functional Requirements:**

#### FR-26: Seed data

PTS can be loaded with fictional seed data: at least three suppliers and enough jobs to show every production status and flag.

#### FR-27: Example supplier files

The repository includes example supplier files with documented expected results. They are used by automated tests and for manual trial.

| File | Content | Expected result |
|---|---|---|
| `valid.xlsx` | Correct updates for several jobs | All rows accepted, changes shown |
| `invalid-status.xlsx` | Unknown status; On hold without reason | Rows rejected (R1, R2) |
| `revision-mismatch.xlsx` | Old revision for a job with a newer revision | W8 |
| `missing-fields.xlsx` | Ready for inspection without type; invalid quantity | Rows rejected (R3, R4) |
| `locked-field-changed.xlsx` | Supplier changed due date and description | W10 |
| `duplicate-job-id.xlsx` | Same Job ID on two rows | Both rows rejected (R7) |
| `missing-job.xlsx` | One exported open job removed | W13 |
| `wrong-template.xlsx` | A column renamed, Export ID removed | File rejected (F2, F3) |

**Consequences (testable):**
- The example files match the seed data: Job IDs and Export IDs in the files exist after seeding.
- Running the automated tests checks each file against its expected result.

## 5. Cross-Cutting Non-Functional Requirements

- **NFR-1 Data integrity.** Job data changes only through FR-1 to FR-4, a manual update (FR-28) or an approved import (FR-18). Approval is all-or-nothing.
- **NFR-2 Traceability.** Every change to supplier-reported fields can be traced, through the job history, to one import log entry or one manual update.
- **NFR-3 Runnable locally.** PTS runs on a single developer machine from the README. It needs no paid services, external accounts or the team's own keys, and has a local database, seed data and example files.
- **NFR-4 Safe file handling.**
  - Only `.xlsx` files are accepted. Macro-enabled files (`.xlsm`) are rejected by F1.
  - Uploads are limited to 5 MB. `[ASSUMPTION]`
  - File content is only read as data and is never executed.
  - Uploaded files are stored only as long as the import exists and its log entry needs them. `[ASSUMPTION]`
- **NFR-5 Responsiveness.** Validating a supplier file of up to 200 rows and showing its change view takes under 5 seconds on a typical laptop. `[ASSUMPTION]`
- **NFR-6 Understandable messages.** Every rejection and warning names its rule ID and says in plain language what is wrong and, where possible, what the value was.
- **NFR-7 Testability.** Every validation rule (F1–F4, R1–R7, W8–W14) and FR-17 are covered by automated tests.
- **NFR-8 Fictional data only.** No real company data, drawings or supplier names in the repository, seed data or example files.
- **NFR-9 Platform.** A desktop web application, used in a current version of Chrome or Edge. Mobile is not supported in v1. `[ASSUMPTION]`
- **NFR-10 Language.** The user interface is in Norwegian in v1. The supplier file stays in English, because its column names are part of the fixed template checked by F2. `[ASSUMPTION]` on the supplier file. The PRD, code and documentation are in English, so UX defines the Norwegian labels for the Glossary terms.

## 6. Non-Goals (Explicit)

- PTS does not replace ERP, PDM, PLM, MES or quality systems, and is not a system of record for engineering or finance.
- PTS does not store engineering drawings as the authoritative source.
- PTS does not send email or integrate with shared folders. File transfer is manual.
- PTS does not give suppliers access to internal systems.
- PTS does not approve technical or quality decisions automatically.
- PTS does not become a warehouse, logistics or financial system.
- PTS does not plan production. It tracks status.

## 7. MVP Scope

### 7.1 In Scope (v1)

- Job register with manual registration of new revisions, manual updates with job history, and minimal supplier management (§4.1)
- Supplier file generation per supplier with the fixed template, pre-filled values, dropdowns and new-revision marking (§4.2)
- Import with file checks, row validation, warnings and change view (§4.3)
- Approval or rejection of whole imports, several pending imports, recalculation and import log (§4.4)
- Dashboard with flags and action filters, including inspection requests (§4.5)
- Seed data and example files (§4.6)

### 7.2 Out of Scope for v1

- Recording inspection results, delivery, internal assembly and final approval — deferred to later versions to protect the core flow this semester.
- Several internal users, roles and login (Windows / Microsoft Entra ID) — later versions.
- Revision history — PTS stores only the current revision.
- Approving or rejecting individual rows in an import — later versions.
- Automatic notification of project manager and job owner on revision changes — later versions.

## 8. Success Metrics

The v1 success criteria are functional and checked by tests and a demo run. SM-N corresponds to success criterion N in the brief.

**Primary**
- **SM-1** — A created job appears on the dashboard with all fields in FR-23. Validates FR-1, FR-23.
- **SM-2** — A supplier file contains only that supplier's open jobs, a unique Export ID and each job's current revision. Validates FR-6, FR-7.
- **SM-3** — Every rejected row is shown with an understandable message naming the broken rule. Validates FR-13, NFR-6.
- **SM-4** — Before approval, the change view shows exactly what changes per job. Validates FR-15.
- **SM-5** — No import changes the database before it is approved, verified by tests. Validates FR-17.
- **SM-6** — A file reporting an older revision is flagged as a revision mismatch. Validates FR-14 (W8).
- **SM-7** — A job whose expected completion date is later than its due date is flagged as delayed. Validates FR-24.
- **SM-8** — When two pending imports share a job and one is approved, the other is recalculated and flagged with W14. Validates FR-19, FR-20.
- **SM-9** — From the dashboard alone, the planner finds all jobs on hold, ready for inspection, delayed, or affected by a new revision. Validates FR-25.
- **SM-10** — Status, on hold reason and inspection type are dropdowns with only the allowed values. Validates FR-9.
- **SM-11** — A new revision is marked on the dashboard and in the next supplier file, and the dashboard mark disappears after export. Validates FR-3, FR-10, FR-24.
- **SM-12** — A file that is not a valid PTS supplier file is rejected as a whole with a clear message. Validates FR-12.

**Secondary**
- **SM-13** — All eight example files produce their expected result in the automated tests. Validates FR-27, NFR-7.
- **SM-14** — The examiner can run PTS and complete UJ-1 and UJ-2 from the README alone. Validates NFR-3.
- **SM-15** — Every change to a job's supplier-reported fields appears in its job history, linked to an import or a manual update. Validates FR-28, NFR-2.

**Counter-metrics (do not optimize)**
- **SM-C1** — Do not reduce the number of warnings shown in order to make imports look clean. Warnings are the point. Counterbalances SM-3 and SM-4.
- **SM-C2** — Do not make approval faster by hiding detail in the change view, for example auto-collapsing warnings or approving by default. Counterbalances SM-4 and SM-5.
