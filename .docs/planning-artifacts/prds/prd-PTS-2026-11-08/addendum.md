# Addendum: PTS PRD

Supporting material for `prd.md`. It belongs downstream (architecture, UX) or is too detailed for the PRD itself. Requirements live in the PRD, and if this file and the PRD disagree, the PRD wins.

| Section | Contents | Main reader |
|---|---|---|
| A1 | How the two Excel templates are built | Whoever builds the supplier file and the job package import |
| A2 | Architecture hints | `bmad-architecture` |
| A3 | Screens and sketches | `bmad-ux` |

**Rule IDs:** the brief numbers its rules 1–15 plus F1–F5. The PRD keeps those numbers and puts a letter in front of rules 1–15 for the kind of rule: R = row rejection (rules 1–7), W = warning (rules 8–15). The file checks F1–F5 keep their IDs. For example, brief rule 8 is PRD W8. Rules 3 and 4 are retired and their IDs are not reused.

## A1. Excel Templates (draft)

- **Files:** `pts-supplier-template.xlsx` (the supplier file, FR-7) and `pts-job-package-template.xlsx` (the job package, FR-31), both generated by `make_template.py`.
- **To regenerate both:** `uv run --with openpyxl python make_template.py`. Optional arguments give the output paths of the two files.
- **Language:** all labels, values and instructions are in Norwegian, per PRD §3.1 and NFR-10. Dates are shown as `dd.mm.yyyy`.
- **Data:** everything is fictional (NFR-8). Drawing numbers look like `DEMO-0101-A001`.

### A1.1 Supplier file

Eight fictional example jobs for *Leverandør Alfa (fiktiv)*, Export ID `EXP-20261125-0001`. The jobs cover every active stage, two stopped jobs, a new revision and a delayed job, so the file can be used to try the rules.

| Sheet | Purpose |
|---|---|
| `Instruksjoner` | Supplier-facing instructions and rules. Protected. Shown first. |
| `Jobber` | One row per open job, sorted by room. Header row frozen, and columns A–E frozen. Columns A–J locked (grey), K–T editable (yellow). |
| `Lister` | Hidden. Allowed values for the two dropdowns. Protected. |

| Columns | Content |
|---|---|
| A–J (locked) | Eksport-ID, Eksportdato, Jobb-ID, Rom, Tegningsnummer, Revisjon, Revisjonsmerknad, Antall ark, Leverandør, Frist |
| K–P (editable) | Material, Sveiset, Kontrollert, Sandblåst, Malt, Sluttkontroll (a date each) |
| Q–R (editable) | Stoppet (*Ja* / *Nei*), Årsak til stopp |
| S–T (editable) | Forventet dato levert, Kommentar / avviksbeskrivelse |

Build details implemented in the draft:

- **Date columns (K–P and S):** data validation of type *date* that requires a date later than 2000-01-01, formatted `dd.mm.yyyy`. The error style is *stop*.
- **Dropdowns:** data validation of type *list* on column Q (*Ja* / *Nei*) and column R (stop reason), referencing `Lister`.
- **Conditional formatting:**
  - red in column R when column Q = *Ja* and R is empty
  - red in column T when column R = *Annet* and T is empty
  - orange in a stage column (L–P) when it has a date but an earlier stage column (from K) is empty. This is a hint for W12. PTS decides on import.
- **New revision:** for a job with a new revision, columns F and G are filled light red with bold dark-red text, and column G shows `NY REVISJON`.
- **Room (D):** stored as text, so room numbers keep their leading zeros.
- **Header comments** explain the stage order, the stopped flag and the revision note.
- **Sheet protection without password.** Excel protection is easy to remove and is a guide only. PTS detects locked-column changes on import (W10).
- **Only data rows are unlocked.** Empty rows stay locked, so suppliers cannot add jobs. A Job ID that is not in PTS is rejected anyway (R6).
- **Not in the file:** area, delivered date and active stage. The active stage is calculated in PTS (A2.1).

Excel data validation applies only to typed input. Pasted values bypass it, and other spreadsheet programs may ignore it. That is why PTS checks every rule again on import (PRD FR-9).

### A1.2 Job package

`pts-job-package-template.xlsx` has the sheets `Instruksjoner` and `Jobbpakke`. The columns are *Rom*, *Område*, *Tegningsnummer*, *Revisjon*, *Antall ark* and *Frist*, with six fictional example rows.

- **Validation:** *Antall ark* must be a whole number of 1 or more, and *Frist* must be a date. Both apply down to row 500, which is the row limit.
- **Skipped rows** and the reasons are decided by PTS on import (FR-31). The file itself does not block them.
- **Rom and Revisjon** are stored as text, so leading zeros are kept.

## A2. Architecture Hints

These are hints, not decisions. `bmad-architecture` makes the decisions.

### A2.1 Data Model

- **Two storage areas** follow from FR-17 and NFR-1:
  - **Staging:** imports and their rows, with validation results.
  - **Job data:** changed only by the approval transaction, a manual update, a delivery or close, or a job register edit.
- **Stored exports.** PTS must store every value in each export. These checks depend on it:
  - W10 compares locked columns with the export.
  - W13 needs the list of jobs in the export.
  - F5 and W9 need the export order per supplier.
  - W14, W15 and FR-8 need the exported values (E, see A2.2).
- **Job history.** W14 and W15 need to know *what* changed a job's current value after the export: an import or a manual update. The job history (FR-5, FR-28) records that.
- **Stage dates and flags.** Store the six stage dates as nullable dates and *Stoppet* as a boolean. The **active stage is calculated** (the first stage without a date) and is never stored, so it cannot disagree with the dates. *Ready for inspection*, *Delayed* and the flags in FR-24 are calculated the same way, except the new-revision mark and the revision mismatch flag, which depend on events.
- **Delivered.** A nullable date set by the planner (FR-29a). A job with a delivered date is closed.
- **Value mapping.** The file uses Norwegian values (PRD §3.1), and storage uses English enums for the stop reason. One mapping table serves export, import (R1) and the UI.
- **Core needs no conflict logic.** In Core a supplier has one pending import and only files from the latest export are accepted (FR-11, FR-12), so D always equals E. Still, put the E/D/F comparison in one function that the Extension reuses for FR-15a and FR-15b.

### A2.2 Three Values per Editable Cell

FR-8, FR-15a, FR-15b, W14 and W15 compare three values for each editable cell:

- **E** — the exported value, stored in the export
- **D** — the current value in job data
- **F** — the value in the returned file

| Case | D vs E | F | Change view | On approval |
|---|---|---|---|---|
| 1 | D = E | F = E | *No change* | Not applied |
| 2 | D = E | F ≠ E | D → F | F applied |
| 3 | D ≠ E | F = E | *Kept*, W14 or W15 as information | Not applied. No choice. |
| 4 | D ≠ E | F ≠ E, F ≠ D | **Conflict field**: D and F side by side, W14 (import) or W15 (manual update) | The planner chooses *Use file value* or *Keep PTS value*. Nothing is preselected, and Approve stays disabled until every conflict field is decided. |
| 5 | D ≠ E | F = D | *No change* | Nothing to apply, and no warning |

Example with a stage date, E = empty, D = 20.11.2026 (manual update after the export):

- F = empty is case 3. The result is *kept 20.11.2026* with W15.
- F = 21.11.2026 is case 4. The planner chooses between 20.11.2026 and 21.11.2026.

### A2.3 Behavior, Stack and Layout

- **Always current:** compute the validation result and change view each time they are shown, by comparing the stored file rows with current job data, not once at upload (principle at the start of PRD §4, and FR-20 in the Extension). For the import log (FR-21), freeze the change view at decision time, including the choice made for each conflict field.
- **Keep it simple:** one web app and one local database (lecturer feedback, criterion 5).
- **Excel library:** the lecturer suggested a common Excel library, for example `openpyxl` in Python or an equivalent in JavaScript. The draft templates use `openpyxl` 3.1.
- **Repository layout (NFR-11):** `testdata/` for example files and seed data. `.gitignore` covers the local database, uploads and generated supplier files.
