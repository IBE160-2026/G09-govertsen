# PRD Quality Review — PRD: Production Tracking System (PTS)

Reviewed: `prd.md` and `addendum.md` (draft, 2026-11-08), checked against product brief v3 (`.docs/planning-artifacts/briefs/PRODUCT_BRIEF.md`) and the rubric in `.claude/skills/bmad-prd/assets/prd-validation-checklist.md`.

## Overall verdict

This is a concrete, well-scoped PRD for a single-operator internal tool. Rule IDs stay stable from brief to PRD, the Glossary does real work, most FRs have testable consequences with worked examples, and SM-1 … SM-12 map one-to-one to brief success criteria 1–12 (verified). The weak spots come from the late changes. FR-28 (manual updates) and NFR-10 (Norwegian UI) were added without updating the parts of the PRD they touch. The result is one direct contradiction about the comparison baseline for imports (FR-8 vs FR-15/FR-20), a Vision statement and Glossary entry that the new FR now contradicts, an undefined language boundary for messages and enum values, and a requirement with no source in the brief that is not flagged as a change from the brief. All of these can be fixed in place. The PRD is close to ready for UX, architecture and stories once the three high findings are fixed.

## Decision-readiness — adequate

Decisions are stated as decisions: "the last approved import wins" (§4.4 description), "Individual rows cannot be approved or rejected" (FR-18), "PTS stores only the current revision" (§3, FR-3). §10 has only two Open Questions, both actually open, and each has an owner or a default. The "Resolved 2026-11-08" list is a good audit trail. Trade-offs are mostly given with what was gained. Only §7.2 says what was given up and why ("to protect the core flow this semester").

The gap is around FR-28. The brief says "**Nothing is written to the database without approval**" (brief §Import rules) and "Only after approval is the database updated" (brief workflow step 6). FR-28 adds a second write path with no approval step. The PRD records this only as one line in §10, "Manual updates of supplier-reported fields are possible (FR-28)". It gives no rationale, does not mark it as a departure from the brief, and the brief was not updated (CLAUDE.md: "Endres et krav, oppdateres PRD-en først" is satisfied, but the trace back to the brief is now broken). There are no `[NOTE FOR PM]` callouts anywhere, even at real tensions such as a manual update being silently overwritten by an older pending file that the planner approves later.

### Findings
- **[high]** FR-28 is a change from the brief but is not labelled as one (§4.1 FR-28, §8 SM-15, §10 "Resolved") — FR-28 and SM-15 have no source in brief v3, and they relax the brief's "Nothing is written to the database without approval" import rule. A lecturer tracing brief → PRD → code will find an FR with no source and a rule that disagrees with the brief, with nothing explaining why. *Fix:* add a short "Changes from the brief" note in §0 (or a `[NOTE FOR PM]` at FR-28) that names the brief rule being relaxed, the reason (information arriving by phone, UJ-4 edge case) and the decision date. Then update the brief, or record it in the brief's change log, so both documents agree.
- **[low]** No `[NOTE FOR PM]` at real tensions (§4.4, FR-20, FR-28) — "last approved import wins" combined with manual updates means an approved older file can undo a phone-confirmed manual update. The only protection is W14. That is a deliberate trade-off and should be visible as one. *Fix:* add one callout at FR-20 stating that W14 is the only guard and that this is accepted for v1.

## Substance over theater — strong

There is no theater here. A single fictional persona (Ingrid) drives every UJ, and every UJ leads to specific FRs. The NFRs have thresholds ("200 rows … under 5 seconds", "5 MB") or concrete mechanisms (NFR-4 `.xlsm` rejected by F1). The Vision is product-specific ("Where is this job, and is there anything we need to act on?"). The Non-Goals in §6 are real boundaries for this domain (ERP/PDM/PLM/MES), not filler.

### Findings
- **[low]** The counter-metrics cannot be measured (§8 SM-C1, SM-C2) — every other SM is "checked by tests and a demo run", but "Do not reduce the number of warnings shown" has no check. *Fix:* turn them into checkable guards, e.g. "the change view never collapses warnings by default; **Approve import** is never the default focused action". They then become UX acceptance criteria.

## Strategic coherence — adequate

The thesis is clear and repeated: "The value is trust in the data" (§1), with the database as the single current picture and every change traceable. The features follow from it. The staging/approval split (FR-17, FR-18), recalculation (FR-20) and the import log (FR-21) all serve that thesis rather than convenience. The MVP is a problem-solving MVP with a stated core flow that must be finished first (§9). The SMs check the thesis (no write before approval, exact change view) rather than activity.

FR-28 has weakened the thesis statement itself, though, and the PRD has not reconciled the two.

### Findings
- **[medium]** The Vision contradicts FR-28 (§1 paragraph 3) — "makes every change traceable to an approved import" is no longer true. NFR-2 now says "to one import log entry or one manual update". Downstream agents quote the Vision. *Fix:* reword to "traceable to an approved import or a recorded manual update".
- **[low]** Key FRs have no SM (§8) — FR-21 (import log) carries the traceability thesis but no SM checks it. SM-8 covers recalculation only after approval, not after a manual update (FR-20/FR-28). *Fix:* extend SM-8 to "approved or manually updated", or add a secondary SM for the import log contents (FR-21 consequence 1).

## Done-ness clarity — adequate

Most FRs have specific consequences with examples (FR-12 "F2: column *Completed quantity* is missing", FR-24 "expected completion date 2026-12-09 and due date 2026-11-27 shows *Delayed*", FR-8 "`In production` and 4"). The example-file table in FR-27 gives stories ready-made acceptance tests. The remaining problems are not vague wording. They are logic gaps where two FRs give different answers, mostly caused by FR-28.

### Findings
- **[high]** FR-8 and FR-15/FR-20 use different baselines for import changes (FR-8 consequence 2; FR-15 "old value (database) and the new value (file)"; FR-20 consequence 1; UJ-5 climax) — FR-8 says "an editable cell whose value equals the exported value produces no change". FR-15 and FR-20 compare file values to the *database*, and UJ-5 says "Monday's file would undo Tuesday's update". These disagree as soon as the database has changed since the export, which is the normal case under FR-20 and FR-28. Under FR-8, Monday's unchanged cells would leave Tuesday's values alone. Under FR-15, they would revert them. This decides how the approval transaction is built and how W14 behaves. *Fix:* decide one rule and state it in FR-15. Either (a) a field changes when the file value differs from the database (then reword FR-8 to "when the database still equals the export"), or (b) a field changes only when the supplier edited it relative to the export (then fix UJ-5's climax and say what the change view shows when the export, database and file all differ).
- **[high]** The language boundary for messages and values is undefined (NFR-10; FR-12, FR-13 example messages; FR-24 flag names; FR-25; §3 enum values) — NFR-10 says the UI is Norwegian and the supplier file is English, and leaves "Norwegian labels for the Glossary terms" to UX. It does not decide: (1) which language the rule messages in the change view use (the FR-12/FR-13 examples are English); (2) whether stored status/reason/type values are English enums shown with Norwegian labels, so that the change view does not show "Database: *I produksjon*" next to "File: *In production*"; (3) which date display format the UI uses (FR-24 and the addendum use ISO, while the resolved question accepts `dd.mm.yyyy`). Tests written from FR-12/FR-13 would assert English strings that the Norwegian UI then contradicts. *Fix:* add consequences to NFR-10: enums are stored as the English template values and displayed with Norwegian labels; rule messages are shown in Norwegian with the rule ID unchanged and English column/value names quoted as they appear in the file; the UI date format is X. Mark the example messages as illustrative of the content, not the wording.
- **[medium]** No rule for conditional fields when the status changes (FR-13 R2/R3, FR-28, UJ-4 edge case, FR-23) — when PTS-0003 goes from *On hold — Missing material* back to *In production* (UJ-4), does the on hold reason stay stored? Nothing says the reason or inspection type must be cleared or must be empty outside its status. FR-23 shows "production status and on hold reason", so a leftover reason would show on the dashboard. This applies to imports and manual updates alike. *Fix:* add to FR-13/FR-28 that the reason (or inspection type) is cleared when the status is no longer `On hold` (or `Ready for inspection`), or that a non-empty value there is a warning or rejection.
- **[medium]** W14 and W9 triggers are ambiguous (FR-14 W14, FR-20 consequences 2–3, UJ-5) — "The affected rows get W14" does not say whether "affected" means rows whose job's fields actually changed or every row whose job appeared in the approved import (including *No change* rows). FR-20 consequence 3 ("If the approved import came from a newer export, the other imports also get W9") conflicts with W9's own definition ("a newer export exists for the same supplier"), which depends on exports, not approvals, and would already hold at upload. UJ-5 calls Tuesday's file "a corrected file". If it is a corrected copy of the same export, W9 does not apply at all. *Fix:* define W14 as "a supplier-reported field of this job changed after upload". Delete FR-20 consequence 3, or restate W9 so it is evaluated on every recalculation. Say in UJ-5 that Tuesday's file came from a newer export.
- **[medium]** Pending imports go stale after FR-2/FR-3 edits (FR-20 trigger list; addendum A2) — FR-20 recalculates only after an approval or a manual update. But editing quantity (R4), supplier (R6), revision (W8) or due date (W11) through FR-2/FR-3 changes validation results too. Addendum A2 says the change view "should be computed from the stored file rows against current job data", which would make the triggers irrelevant. The PRD and addendum describe two different models. *Fix:* state in FR-20 that validation and the change view of every pending import always reflect current job data (any job edit). Keep W14 only for changes to supplier-reported fields.
- **[medium]** The revision-mismatch flag fires after a normal revision change (FR-24 Revision mismatch, FR-3) — the flag is "the last approved import for the job reported a revision other than the current one". After Ingrid changes C → D (FR-3), the last import reported C, so the job immediately shows both *New revision* and *Revision mismatch*, although the supplier has done nothing wrong. It is also unclear whether a rejected row's reported revision counts. *Fix:* only raise the mismatch flag from imports approved after the current revision was set, and say that rejected rows do not count.
- **[low]** Some FRs have no testable consequences (FR-5, FR-16, FR-26) and FR-22 is incomplete — FR-5 and FR-16 have no consequences block. FR-22 says the user name is recorded "on every approval or rejection", but FR-28 also depends on it for manual updates. *Fix:* add one consequence each and extend FR-22 to manual updates.
- **[low]** Edge rules are unstated (FR-13, FR-14 W12, F3) — `Completed` is allowed with completed quantity below quantity. W12's baseline (database or export) is not given. A file whose rows carry different Export IDs is not covered by F3. *Fix:* decide each in one line, or tag it `[ASSUMPTION]`.

## Scope honesty — adequate

The Non-Goals in §6 and Out of Scope in §7.2 are explicit, and assumptions are tagged inline and indexed. The open-items count (2 open questions, 13 assumptions, 0 PM notes) suits a semester project. One silent omission matters, and one Glossary statement is now false.

### Findings
- **[medium]** There is no way to cancel or remove a job, and "not closed manually" is no longer true (§3 *Open job*; FR-1, FR-2, FR-28) — the Glossary says "Jobs are not closed manually in v1", but FR-28 lets the planner set `Completed` by hand, which closes the job. A mistakenly created or cancelled job has no exit except a false `Completed`, and until then it appears in every supplier file (FR-6). *Fix:* either add cancel/delete for jobs never exported, or add a `[NON-GOAL for MVP]` saying wrong jobs are closed by a manual update to `Completed`. Update the Glossary sentence either way.
- **[low]** Some gaps in traceability are not declared (NFR-2, FR-12, FR-2) — file-check rejections create no import and so leave no log entry. FR-2 edits to due date, quantity or supplier and FR-3 revision changes are not in any history. Both are reasonable for v1 but are not written down as decisions. *Fix:* add one line to §7.2 saying only supplier-reported fields are historized.
- **[low]** The delete rule has no delete function (FR-4) — "A supplier with jobs cannot be deleted", but FR-4 only grants create and list. *Fix:* add delete (and rename?) to FR-4, or drop the consequence.

## Downstream usability — adequate

The Glossary is complete for the import domain and is mostly used word for word. FR-1 … FR-28, F1–F4, R1–R7 and W8–W14 are unique and contiguous, and the brief → PRD rule mapping in addendum A4 is correct. Each UJ names Ingrid and lists what realizes it. The weak points are a few cross-references and seed data that cannot support the example files as written.

### Findings
- **[medium]** Seed data cannot support the example files as specified (FR-26, FR-27 consequence 1; addendum A2) — FR-26 asks only for suppliers and jobs. But F3 requires an Export ID "generated by PTS", W10 and W13 compare against the stored export, `revision-mismatch.xlsx` needs an export taken before a revision change, and W9 needs two exports for one supplier. Unless seeding creates matching export records with their stored values, SM-13 cannot pass. *Fix:* extend FR-26 to "seed data includes the exports (with their stored rows) that the example files in FR-27 were generated from, including one supplier with two exports and one job whose revision changed after export".
- **[medium]** The UJ-3 cross-reference is wrong (§2.4 UJ-3 "Realized by FR-3, FR-8, FR-9, FR-15 (W8)") — W8 is defined in FR-14, not FR-15. FR-8 and FR-9 (pre-fill, dropdowns) are not part of this journey. FR-10 (marking and clearing in the file) and FR-24 (badge) are, and they are missing. Story creation will pull the wrong FRs into this journey's epic. *Fix:* "Realized by FR-3, FR-10, FR-14 (W8), FR-24".
- **[low]** Terms and definitions drift (FR-10, §3, NFR-1, §4.1) — FR-10 defines the marked state as "current revision changed since the previous export to its supplier", while §3 defines a *new-revision mark* set by FR-3. These differ for B → C → B before export. "Job register" is used as a product area (§4.1, FR-5, §7.1, §10 Q1) but is not in the Glossary, and FR-5 suggests it is a different view from the Dashboard. NFR-1 lists FR-4 (suppliers) as a way job data changes and leaves out FR-10, which clears the mark. *Fix:* make FR-10 say "has a new-revision mark", add *Job register* to the Glossary, and correct NFR-1's list.

## Shape fit — strong

The shape fits a single-operator internal tool that feeds UX, architecture and stories. Five short UJs with one persona are not overhead here. UJ-2 and UJ-5 carry edge cases (whole-file rejection, two pending imports) that FR-19/FR-20 depend on. The SMs are operational and checked by tests, which suits a course project with no live users. The addendum correctly takes template build details and architecture hints out of the PRD and says that the PRD wins where they disagree. No findings.

## Mechanical notes

- **SM → brief mapping:** SM-1 … SM-12 match brief success criteria 1–12 in order and content (checked line by line). SM-13 … SM-15 are PRD additions; SM-15 traces to FR-28, which has no brief source (see Decision-readiness).
- **Rule IDs:** F1–F4, R1–R7 and W8–W14 match the brief's numbering, and addendum A4 explains the letter prefixes. FR-28 cites "R1–R5", which is correct, since R6/R7 are file-only.
- **FR ordering:** FR-28 sits in §4.1 between FR-5 and FR-6. The IDs are unique, but the numbers jump within the document. That is acceptable if the stable ID is intended. Add a note in §0 that IDs are append-only.
- **Small wording drift:** the Glossary says the mark is cleared when a file "has been generated", while UJ-1 and UJ-3 say "downloaded". FR-6 makes generate and download one action, so this is harmless. FR-2 "Realizes UJ-1", but UJ-1 has no edit step.
- **Assumptions Index roundtrip:** every inline `[ASSUMPTION]` is indexed and every index entry appears inline. Two small issues: the index entry "§3 / FR-1" has no tag at FR-1 itself, and the index is not in document order (FR-25 is listed before FR-4).
- **NFR-4 storage assumption:** "kept as long as … log entry needs them" combined with FR-21's permanent log effectively means the file is kept forever. Say so explicitly.
- **Required sections:** all are present for the stakes (Vision, Users, UJs, Glossary, Features/FRs, NFRs, Non-Goals, MVP Scope, SMs with counter-metrics, Constraints, Open Questions, Assumptions Index).
